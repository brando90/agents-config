# INDEX_RULES.md — Global Rules & Doc Routing
**TLDR:** This file defines global agent rules and routes agents to the machine, workflow, and writing docs relevant to the current task.

Load only the docs relevant to your current task.

**Remote fallback:** If `~/agents-config/` is not available locally (e.g., running in a cloud sandbox or on the phone), fetch any needed files from `https://raw.githubusercontent.com/brando90/agents-config/main/`. This applies to this file, all machine docs, all workflow docs, and anything else referenced below.

## Hard Rules (every response, never skip)

These rules apply to EVERY agent response and EVERY session. Violating any of these is a failure.

1. **Never commit secrets — default is NEVER, even when explicitly asked.** Before any commit (and before any auto-push backstop), scan staged files for: API keys, tokens, passwords, `.env*` (including `.env.local`, `.env.prod`, etc.), `*.pem`, `*.key`, `id_rsa*`, `credentials*`, anything under `~/keys/`, and high-entropy values assigned to names matching `(api[_-]?key|token|password|secret|auth|bearer)\s*[:=]\s*["']?[A-Za-z0-9_\-/+]{16,}`. If anything matches, abort the commit and tell the user exactly which file/line. Once a secret is pushed it must be assumed compromised — git history can't be fully purged (history rewrite + force-push + every existing clone keeps re-leaking), so rotate the credential immediately rather than trying to "scrub" it. **Even an explicit user override ("just commit it") should get pushback first**; the user has stated they don't want to be saying that, so treat such requests as a likely mistake and confirm twice before honoring, then still rotate the credential after. Use env vars or reference `~/keys/` / `~/.ssh/config` instead of inlining secrets.
2. **Verify before pushing.** Review diffs for secrets, unintended changes, broken imports.
3. **Run proportionate QA before reporting any non-trivial task as done.** Pick the lightest QA tier that covers the risk. Routine prose / paper wording / markdown-doc edits use lightweight deterministic checks by default: self-review the diff, `git diff --check`, and run the relevant compile/render/grep/link checks. Do **not** dispatch fallback model reviewers for ordinary writing polish just because one reviewer stalled. Dispatch one independent reviewer (A1 builds → A2 reviews/fixes) for code/behavior changes, scripts, infra/auth, data/result changes, headline claims/numbers/tables/citations, nontrivial shared workflow/rule changes, final/pre-submission gates, or when scientific/behavioral correctness is uncertain. **Round budget (Brando 2026-08-20): ONE opposite-agent review round is the default AND usually the end** — builder's opposite CLI reviews (CC built → Codex reviews; Codex built → CC reviews), the builder applies the fixes, verifies them with deterministic checks (tests/compile/grep), done. Do **not** dispatch a re-review of the fixes by default. Escalate to a **second** round (X → Y → X → Y → X → done) only for the hardest changes — eval/scoring integrity, security/auth surfaces, or when the first round's findings forced risky fixes — and **never beyond two rounds without Brando asking**: multi-round chains drain the token budget ("otherwise I run out of tokens"). Mega QA remains opt-in via Trigger Rule 10 and is **manual-only by Brando** — an agent never selects it. **CLI-only, no API keys.** Any reviewer dispatch must use locally logged-in approved CLIs (`codex`, `clauded`) with cached subscription/OAuth credentials; never fall back to `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` / `GEMINI_API_KEY`. The deprecated Gemini CLI must not be used. Claude and Codex remain the preferred review families; Brando's September 11 cross-provider recovery authorization also permits other verified subscription clients under Trigger Rule 48 where the canonical review procedure allows them. Explicit required families and benchmark-reference acceptance are unchanged. See [`workflows/qa-correctness.md`](workflows/qa-correctness.md) for tiers and [`workflows/qa-structural.md`](workflows/qa-structural.md) for structural checks.
4. **Dual TLDR: one at the top, one at the end.** Every response must open with a `**TLDR-start:**` line and end with a `**TLDR-end:**` line — 1–2 sentences each. The top TLDR exists so the user sees a summary in preview / prefix-s mode without scrolling. The bottom TLDR is the authoritative one: it must be written last, from the actual response content, **ignoring what was written in `TLDR-start`**. Do not copy-paste `TLDR-start` into `TLDR-end`. If the chain-of-thought in the response changed your conclusion, `TLDR-end` should reflect that change — divergence between the two is expected and fine. If only one TLDR is present, it must be `TLDR-end` (never only `TLDR-start`). **Project tag:** prefix **both** TLDRs with a square-bracket tag in the format `[proj: task]` — **project first**, then the current task; if there is no clear task yet, project only: `[proj]`. Use a concise/abbreviated project name (e.g. `vb` for veribench, `beyond-scale`) — e.g. `**TLDR-start:** [vb: leap-gemini-key] …` — so Brando can tell which project/conversation a response belongs to from the TLDR alone (he reviews many per day and otherwise cannot place them). Lean on the project as the anchor; the task part is secondary and should change as the conversation's task changes. Keep the whole tag short, and outside the 1–2 sentence budget. Applies to all agents (Claude Code, Codex, etc.). No exceptions.
5. **Verification snapshot after TLDR-end.** Immediately after `TLDR-end`, append a `**Snapshot:**` block — a small, concrete, inspectable sample of the actual artifacts the task produced, so the user can visually confirm the work was really done without re-running commands. Target ~5–15 lines total; hard cap 25. Pick the *smallest representative sample of real output*, not a restatement of the TLDR and not an abstract description. Examples: 3–5 rows of a generated table/dict, first/last lines of a written file plus its path and size, URLs of pushed commits/PRs, the diff's `--stat` summary, a directory listing of new files, the exact command executed and its first few lines of output. For intangible tasks (a decision, explanation, refusal) include a one-line before/after or a cited file path + line range. If there is genuinely nothing to show, write `**Snapshot:** _(nothing to show — [brief reason])_` — do not silently omit. Applies to all agents.
6. **Refresh agents-config before each new user task.** At the start of every non-trivial user request: (1) `git -C ~/agents-config pull` to fetch remote changes, (2) re-read `~/agents-config/INDEX_RULES.md` into your active context so the current session has the latest rules and doc references, (3) if the pull brought changes, also re-read any changed machine or workflow files relevant to your current environment. For long sessions (over 1 hour), also refresh mid-task — check with `date` and compare to your last pull. Push any uncommitted agents-config changes and run QA if changes were pulled from another agent.
7. **Agent CLI freshness.** Claude Code's `SessionStart` hook (`~/.claude/settings.json`) runs `~/agents-config/scripts/auto-update-tools.sh` on every session start. Major CLIs: `codex`, `claude` / `clauded`, `antigravity` (Google — replaces the deprecated Gemini CLI; install per https://antigravity.google). The old Gemini CLI must not be installed or used. Example extras: Cursor, Mistral, Harmonic, Axiom, and similar installed tools. If one looks stale, use the right package manager or print a one-line reminder with the exact update command. Never assume `npm` for a Homebrew-installed binary.
8. **Strong masters; proportionate execution workers; bounded review and quota recovery.** Keep the strongest configured model for masters and reasoning-critical work. A master explicitly chooses each worker's model and effort for its phase; capable regular workers are the default for well-specified execution. A detailed handoff reduces ambiguity, not the required standard of correctness. Do not lower global defaults to dispatch a worker. Trigger Rule 48 and [`workflows/reliable-agent-dispatch.md`](workflows/reliable-agent-dispatch.md) define the completion budget, verified handoff and cross-provider recovery contract.
    - **Pinned defaults:** Codex `gpt-6-astra` with `model_reasoning_effort = "ultra"` in `~/.codex/config.toml`; dispatch with `codex exec --approve-for-me -m gpt-6-astra -c 'model_reasoning_effort="ultra"' "$QA_PROMPT"`. Claude Code `claude-fable-5-1` with `"effortLevel": "max"` in `~/.claude/settings.json` ([template](claude-code-settings.json)); dispatch with `claude -p --model claude-fable-5-1 --effort max` (`claude-fable-5-1[1m]` for the one-million-token context variant). Use `-s read-only` for a Codex review that must not edit; `--full-auto` is removed. Follow Trigger Rule 42 for unattended worker permissions and isolation.
    - **Worker selection:** separate planning, routine execution, the model being measured, and acceptance review. Prefer direct commands for deterministic work; for bounded implementation or research with clear inputs/tests, select a regular reasoning worker and supported effort explicitly. Escalate difficult decisions to the master or a stronger worker based on evidence. Reserve shared subscription allowance for remaining work, reviews and publication; do not send every remote worker at the master's maximum effort. Record exact selected and actual settings, role, rationale and eligible substitutes under Rule 48.
    - **Reviewer selection:** prefer the strongest reviewer from the other company. For ordinary changes, if that model cannot run, try one suitable smaller reasoning model from that company before a fresh strongest-model review from the builder's company. Report the capability reduction and why the candidate meets the task's review needs. A model-specific failure does not prove provider-wide exhaustion. Do not probe smaller models when a provider-wide failure is established. The canonical decision procedure, attempt budget, and reporting fields are in [`workflows/qa-correctness.md` § Review fallback and acceptance](workflows/qa-correctness.md#review-fallback-and-acceptance); apply it to every review dispatch, including Mega QA.
    - **Acceptance limits:** critical changes retain a strongest-model acceptance review; a smaller critic is advisory only. This includes benchmark reference data, evaluation/scoring integrity, security/authentication, permissions or spending controls, substantive scientific claims/results, uncertain correctness, and shared rules controlling review, permissions, spending, or publication. Each explicitly requested Mega QA acceptance stage also retains the strongest-model requirement. Trigger Rule 43 still requires **both model families at their strongest tier** for every accepted benchmark reference change. A same-company fallback never satisfies a mandatory cross-company check. Keep unresolved requirements pending, even if useful work continues. Model agreement or company diversity is not proof of correctness; reconcile findings against requirements and deterministic checks.
    - **Experiment workloads:** the evaluation backbone, agent under test, evaluation judge, and bulk generation default to regular thinking models such as Claude `claude-sonnet-5` or Codex `gpt-5.6-terra`. Escalate when needed or when Brando explicitly requests a flagship model; record the exact model identifier in results. A benchmark reference edit follows Trigger Rule 43 instead. For executor subscription exhaustion, follow Rule 48: checkpoint, fence the old writer, transfer to an eligible verified subscription client, verify continuation and notify. This never silently changes a pinned model under evaluation, judge, effort, dataset or scoring protocol. If no eligible executor remains, preserve state, notify and arrange a real bounded retry where possible.
    - **Human handoffs:** recommend model and effort proportionately to scope and risk, outside the prompt (Trigger Rule 36). A small mechanical edit may use a regular model; critical review retains the strongest tier. Explicit user model requirements take precedence over fallback; report a blocked required model instead of silently substituting it.
    - **No paid escape hatch:** all model work stays on approved authenticated subscription command-line interfaces (CLIs), per Hard Rule 9. Never use provider application programming interface (API) keys or purchase extra credits to bypass exhaustion. If no eligible reviewer can run within the bounded attempts, report what completed and which acceptance requirement remains unmet.
    - **Keep defaults synchronized:** when the designated strongest models change, update this rule, `~/agents-config/CLAUDE.md`, `~/agents-config/AGENTS.md`, [`workflows/qa-correctness.md`](workflows/qa-correctness.md), [`machine/macos-ai-apps/ai_agent_automatable_setup_codex_clauded.md`](machine/macos-ai-apps/ai_agent_automatable_setup_codex_clauded.md), [`claude-code-settings.json`](claude-code-settings.json), and `~/.codex/config.toml` together. Agent entry points summarize and link here; do not copy the full fallback procedure into each document.
9. **CLI-only for all LLM work — no agent-authored direct API calls.** Extends the CLI-only mandate from Hard Rule 3 (QA dispatch) to **every** LLM-driven action in every session. **Allowed:** dispatch via the locally-authenticated CLIs `clauded` / `codex exec` / `antigravity`, which use cached subscription / OAuth credentials, are billed against the user's CLI plan with effective per-session ceilings, and leave observable transcripts. The deprecated Gemini CLI is not approved; use a working supported subscription client for Google models. Under Brando's September 11 authorization and Trigger Rule 48, Cursor-hosted models, Grok or other providers may also execute eligible work when their exact client/model, target-host authentication, tools, data access and subscription-only billing are verified. This is not permission to use arbitrary API endpoints, new paid credits or unverified clients. **Forbidden:** authoring or executing any direct LLM-provider API call (`anthropic.messages.create`, `openai.chat.completions.create`, `litellm.completion`, `google.genai.Client(...)`, raw `requests.post` to `api.anthropic.com` / `api.openai.com` / `generativelanguage.googleapis.com`, etc.) unless **Brando wrote the call himself**. An agent must never *author* such code — not in a new script, not in a refactor, not in a one-off notebook cell. Before *executing* any existing script that loads `~/keys/anthropic_*` / `~/keys/openai_*` / `~/keys/gemini_*` / `~/keys/aristotle_*` or sets `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` / `GEMINI_API_KEY`, the agent MUST pause, surface the script path + estimated spend + which experiments will run, and wait for explicit confirmation — silent runs are the failure mode. **Why:** API keys bill per-token with no cap. One agent-driven default (Opus 4.7 in an agent loop, no Batch API discount, ~30 callers all defaulting to the same key) burned **$17,752.98 in 25 days** against `anthropic_bm_key_koyejolab` in May 2026, and the lab confirmed on 2026-05-25 that it cannot absorb that scale of spend. CLI subscriptions self-throttle when a loop misbehaves; raw API self-bills until it drains the account. **How to apply:** (a) if you are about to write `Anthropic(...)` / `OpenAI(...)` / `genai.Client(...)` / `litellm.completion(...)` or paste an `sk-ant-` / `sk-` key into a script, stop and ask Brando whether to use `clauded -p "$PROMPT"` / `codex exec --approve-for-me -m gpt-6-astra -c 'model_reasoning_effort="ultra"' "$PROMPT"` instead; (b) when reviewing diffs or QA'ing code, flag any agent-authored direct API call as a CRITICAL issue blocking merge; (c) before running any script that reads from `~/keys/*` for an LLM provider, surface path + back-of-envelope cost (`tasks × calls × ~$0.003 Sonnet input / ~$0.015 Opus input` per 1K tokens, multiplied by ~1–10 reps) and wait. **Exception:** Brando-authored API-calling code (commit author = Brando, or explicit "I wrote this, run it now" instruction from Brando in the current prompt) — you may execute it, but still surface estimated spend first. **Counterexample (NOT a direct API call):** invocations of the `clauded` / `codex` / `antigravity` CLIs are exempt, even though they internally reach Anthropic / OpenAI / Google — they are subscription-billed and observable in local transcripts.
10. **Expand every acronym and define every piece of jargon on FIRST USE, in every response.** Applies to ordinary chat replies, not just to papers and reader-facing prose. The first time an abbreviation, initialism, or project-specific term appears in a response, write it out and say what it means in one short clause: `TBH (to be honest)`, `SCSC (Smooth Conjunctive Score for Code verification)`, `IC_pp (fraction of the agent's stated theorems it actually proved)`, `the fresh re-run` (rather than an in-house label like "Arm 2" that means nothing outside the experiment folder). Casual abbreviations count: `tbh`, `iirc`, `afaict`, `wrt`, `ETA`, `EOD`. So do metric symbols, factor names, experiment-internal vocabulary, file/label identifiers, and any term whose meaning depends on a document the reader is not currently looking at. Use the expansion once, then the short form freely for the rest of that response; re-expand in the next response, since Brando may be reading it on its own. **The trap this closes:** an agent reads an experiment README or a results summary, absorbs its private vocabulary, and then writes as if that vocabulary were shared -- but Brando is reading the reply, not the file the agent just read. **Why:** stated by Brando 2026-09-02 after a reply built an entire analysis on the in-house labels "Arm 1" / "Arm 2" without ever saying what they meant, leaving him to ask whether it meant the ARM hardware architecture. **Borrowed metaphors are jargon too:** "arm" there was the clinical-trial sense (one branch of an experiment), which is useless to a reader who is not running clinical trials -- the fix was not to define it but to rename it to what it actually was, a rescore of old runs versus a fresh re-run: "tell me what acronyms mean. I don't know what you're talking about" and "otherwise I don't know what the fuck you're talking about in your responses agents!" An unexplained acronym silently transfers the agent's work onto the reader. **Distinct from Trigger Rules 23 and 24**, which govern jargon in *reader-facing prose* (papers, blog posts); this Hard Rule governs every response the agent writes, to anyone, including Brando.

## Trigger Rules (mandatory when triggered)

These rules fire in specific contexts. When the trigger condition is met, they are mandatory.

6. **Commit, push, and re-read agents-config after any edit.** _Trigger: you or the user modify any file under `~/agents-config/`._ (1) Re-read the changed file(s) so your context stays current for the rest of the conversation. (2) Commit and push to the remote before continuing with the next task — other agents on other machines pull from this repo, so stale config causes drift. Also ensure project-level config files that reference agents-config (e.g., a project's `CLAUDE.md`) stay consistent.
7. **Keep PRs short.** _Trigger: creating a pull request._ The PR description must start with a **Summary** section of 5–10 bullet points max (one line each). Follow with a short **Test plan** (2–3 bullets). Include links (W&B Report URLs, relevant docs). After these two sections, an optional **Appendix** may contain extended details, file lists, or context — but assume the reader stops after the summary. No walls of text.
8. **Commit and push after QA passes.** _Trigger: QA verdict is PASS or FIXED with 0 critical issues._ Immediately `git commit` and `git push` without asking the user. Only escalate to the human if the QA verdict includes critical issues (CRITICAL_ISSUES > 0) or is FAIL. Major-only issues in non-active files (archives, historical results) do not block the commit.
9. **GPU discipline: baseline → estimate → ask → verify → clean up.** _Trigger: about to launch a GPU job._ Before launching any experiment on a GPU, first run or reason from a 1-device baseline whenever practical. Report to the user: (a) estimated VRAM, (b) expected utilization pattern (compute-bound vs CPU/IO-bound), and (c) estimated duration, or explicitly state that the duration is unknown. If the workload appears mostly CPU or IO bound, or uses only brief compute bursts, say so clearly and suggest a smaller machine or a CPU-only node. Do not silently claim multiple devices. Present the per-device allocation plan and wait for user approval. Hardware allows sharing, but PyTorch's caching allocator means memory footprints can spike unpredictably, causing OOM crashes for others. Furthermore, spreading low-utilization work across multiple devices hogs the system's PCIe bandwidth. Therefore, the etiquette rule is: a small memory footprint on one shared device is fine; spreading low-utilization work across multiple devices, or holding idle devices for long durations, must be avoided. **Hard Rule:** The agent MUST explicitly set `export CUDA_VISIBLE_DEVICES=<chosen_ids>` in the bash environment before executing any python script. Verify with `nvidia-smi` within a few minutes of launch. If utilization stays persistently low, report it to the user and suggest consolidating, fixing the input pipeline, or moving off the device. After completion, clean up orphaned processes and report the final state. See [`workflows/expts-and-results.md`](workflows/expts-and-results.md) § Allocation Rules and § Post-Experiment Cleanup.
10. **Mega QA: sequential multi-model review chain.** _Trigger: user **explicitly** says "mega QA", "super QA", "extra careful QA", "deep QA", "final QA", "pre-arXiv QA", "pre-submission QA", or similar. Never auto-triggered — not by `git push`/merge to `main`, not by file-path heuristics, not by a project QA-gate hook. Push-to-`main` gates default to the lightest proportionate tier (Hard Rule 3) and may require Tier 1/2 QA, but must never invoke the mega chain on their own; only an explicit user request (or a user-set opt-in such as a `[mega-qa]` commit tag) starts it._ Instead of the default single-reviewer QA, run approved reviewer passes **sequentially** — each does full QA (correctness + structural, with authority to fix), then passes the improved code to the next. Default chain (3 stages, preferred Claude/Codex chain; any eligible substitute follows the canonical review procedure and Rule 48): Codex → CC → Codex (if CC built) or CC → Codex → CC (if Codex built) — the builder reviews in the middle (knows intent best); the non-builder CLI takes the first and last (clean-eyes) passes in fresh contexts. If the user asks for more rounds, cycle the chain in fresh contexts. **Per-stage fallback:** apply Hard Rule 8 and the canonical [review fallback procedure](workflows/qa-correctness.md#review-fallback-and-acceptance). Complete the planned stages using eligible reviewers; an advisory smaller-model pass cannot fill a stage requiring a strongest-model reviewer. Preserve mandatory cross-company checks, including Trigger Rule 43. If no eligible reviewer can run, stop and report the incomplete stage; never claim acceptance from stage count alone or use provider keys. **Manual-only (Brando 2026-08-20):** the mega chain runs only when Brando himself types a trigger; an agent must never choose it on its own — not for end-of-day, pre-merge, pre-sleep, or "high-stakes" moments. For everything an agent decides itself, the Hard Rule 3 round budget applies (one opposite-agent round default, two max for the hardest). See [`workflows/qa-correctness.md`](workflows/qa-correctness.md) § Mega QA.
11. **Publish ultimate-utils to PyPI after QA-gated push to `master`.** _Trigger: QA passes on `~/ultimate-utils/` and changes are pushed to `master`._ After the QA-approved code is on `master`: (1) bump the `version` field in `~/ultimate-utils/pyproject.toml` (patch increment, e.g., `0.10.3` → `0.10.4`), (2) commit and push the version bump to `master`, (3) build and upload: `cd ~/ultimate-utils && bash scripts/publish_to_pypi.sh` (handles token auth from `~/keys/push-pypi-all.txt`, builds, checks, and uploads). This keeps Git and PyPI in sync so other machines and downstream users get the latest via `pip install ultimate-utils --upgrade`.
12. **Clean up idle background processes (>24h, confirmed idle).** _Trigger: starting a new session, or starting new monitors/workers._ Before spawning new background processes, scan for existing ones (`ps aux | grep -E "(tail -f|run_worker|until.*sleep.*done)" | grep -v grep`). For each candidate, run a health check before killing — **never kill blindly**: (1) CPU time delta — sample `ps -p $PID -o cputime=` twice 10s apart; if cputime increased, it's actively computing, don't kill (single-sample `%cpu` is unreliable between bursts). (2) Has child processes (`pgrep -P $PID`)? → don't kill. (3) For workers: DB has claimed jobs? → don't kill. (4) For `tail -f`: log file modified in last hour? → don't kill. (5) For `until` loops: wait condition already met? → stuck, safe to kill. **Only kill if ALL checks confirm idle AND running >24h.** Also: name processes descriptively when spawning them so future agents can inspect purpose from `ps aux`. ScheduleWakeup loops must self-terminate when their condition is met.
13. **Load ML writing guide for top-venue paper work.** _Trigger: any NeurIPS / ICML / ICLR-style paper work, including editing `.tex`, adding claims/numbers/tables, deciding which artifacts to cite or keep, or answering proof/result-validity questions._ Before acting, read [`writing/ml_research/ml_research_writing.md`](writing/ml_research/ml_research_writing.md) and apply its Scientific Rigor and Sentence-Level Prose Discipline. For any sentence that ships in the paper, run the 4-check (read-aloud / claim-count / citation-count / word-count) while drafting, not during QA.
14. **Email tracked completions and authorized quota-recovery events to Brando.** _Trigger: (a) a user-triggered "mega QA", "deep QA", "big QA", or similar substantial QA pass finishes, OR (b) Brando explicitly asked for email/notification/tracking on completion, including the standing remote-worker completion instruction in Trigger Rule 46, OR (c) a remote quota-risk, provider-handoff or exhausted-recovery event under Trigger Rule 48._ Send one concise email to `brando.science@gmail.com` after the relevant state is verified (completion after final QA/commit/push; a Rule 48 recovery event promptly when it occurs). Do not CC Brando's personal email on internal agent notifications unless Brando explicitly asks for it; see Trigger Rule 26. If Telegram triggered or approved the task, also send a one-line Telegram completion message in the originating chat.
    - **Quota/recovery notices:** Rule 48 authorizes deduplicated warnings, handoff outcomes and exhausted-recovery notices to the master and `brando.science@gmail.com`; do not wait for task completion or email unchanged polls.
    - **Default QA is not enough.** The normal QA required by Hard Rule 3 does NOT by itself trigger email. Ordinary requests should finish in chat without an extra mailbox round trip.
    - **Paper/research edits are not automatic email triggers.** Email only if the edit was part of a user-triggered big/mega QA pass or Brando explicitly requested email notification. Routine manuscript edits, table fixes, exploratory reads, and result lookups should report in chat/Telegram only.
    - **Significant by itself is not enough.** Multi-hour, long-running, or high-stakes work still does not email unless it is user-triggered big/mega QA or Brando explicitly says to notify/email/track completion (including Trigger Rule 46). If unsure, do not email; summarize in the current chat.
15. **Q&A stays in chat unless explicitly emailed.** _Trigger: the user asks a substantive question._ Answer the question in the normal response and do not send an email by default. If Brando explicitly says to email the answer, send one email to `brando.science@gmail.com` only, with no CC unless the prompt names additional recipients. **Subject:** `Q -> A: <brief question> -> <brief answer>`. **Body:** Start with `TLDR: <1 sentence>`, then write in natural conversational prose. Skip email for ordinary clarification, diagnosis, or "why did this happen?" questions; otherwise requests become slower and every debugging conversation turns into mailbox noise.
16. **Document headers: title + 1–2 sentence TLDR on every generated doc.** _Trigger: you create a new document or substantially rewrite one (any `.md`, `.txt`, `.rst`; design docs, plans, READMEs, reports, summaries, postmortems, eval writeups)._ The first non-blank line of the file MUST be a `# Title` heading describing the doc's purpose, and immediately under it a `**TLDR:**` block of 1–2 sentences summarizing the document. Why: Brando reviews many auto-generated docs per day and cannot read every body — a missing or weak TLDR makes the work unverifiable in practice ("otherwise it's too much shit to verify"). Applies whether the doc is committed, only staged, or kept locally. Applies to docs you author or substantially rewrite, not to docs you only spot-edit. For very short docs (< ~20 lines) a one-line `**TLDR:**` is sufficient. **A more-specific artifact format overrides this length.** Where another rule or workflow doc specifies a fuller header for a particular file type — notably the 2-6 sentence `cc.md` prompt-file TLDR in [`workflows/expts-and-results.md`](workflows/expts-and-results.md) § Agent Prompt format, which must cover what the agent does, the success criterion, the deliverable, and any load-bearing constraint — that longer spec governs and is not a violation of this rule. The 1-2 sentence form is the default for ordinary docs, not a cap on specialized ones. **Distinct from Hard Rule 4:** Rule 4 is the response-level Dual TLDR for chat output; Rule 15 is the file-level Title + TLDR for documents you write to disk. Both apply when you generate a doc inside a response — the chat gets `TLDR-start`/`TLDR-end`; the file gets `# Title` + `**TLDR:**`.
17. **Run user tasks end-to-end; never ask mid-task.** _Trigger: any user task._ Flow: smoke → full E2E → proportionate QA (Hard Rule 3) → commit + `git push` (Trigger Rule 8) → only then surface to the user. If mid-task verification is needed, run the deterministic checks for the task first; dispatch a reviewer only when the selected QA tier calls for it. Halt at smoke only on explicit ask ("smoke only", "stop after smoke").

40. **Every committed slide deck ships a synced PDF (and, for `.pptx`, a text dump) beside it.** _Trigger: you add, edit, or commit a `.pptx` / `.key` / `.ppt` / `.odp` slide deck in any repo — including a deck downloaded from Google Slides or Keynote and dropped into an experiment folder._ Binary decks are invisible inside Cursor / VS Code: the editor cannot render them, `grep` cannot read them, and `git diff` shows only "Binary files differ". So each committed deck carries generated siblings, regenerated from the deck and committed **in the same commit as the deck**:
    - **`<deck>.pptx.pdf`** — the rendered slides, for every deck format. Cursor opens these inline via the `tomoki1207.pdf` extension, so this is how a deck is actually *looked at* in the editor.
    - **`<deck>.pptx.md`** — a slide-by-slide text outline (titles, nested bullets, tables, speaker notes, image counts). **`.pptx` only:** `.key` is a proprietary format and `.ppt` / `.odp` are different containers, so those get the PDF and full freshness tracking but no text sibling. Keynote directory packages must first be exported as single-file `.key` decks; both checks reject package directories rather than silently omitting them. The text dump is what makes a deck greppable and gives it a **readable line-level `git diff`** instead of a binary blob.

    **Command:** `python3 ~/agents-config/scripts/sync_slide_decks.py` — with no arguments it syncs every deck under the current git repo root; `--check` verifies the working tree; `--check-staged` verifies **git's index** and is what the pre-commit hook runs; `--md-only` skips rendering when no converter is installed; `--force` regenerates everything. Python 3.8+ standard library only, so it runs on any machine with `python3` (no `pip install`, which matters under PEP 668).

    **Naming is `<full source filename> + .pdf` / `+ .md`**, keeping the deck's own extension in the middle — `Thesis Plan.pptx` → `Thesis Plan.pptx.pdf`. That survives filenames with spaces, parentheses, em-dashes and trailing spaces (Brando's decks have all four), makes the derivation unambiguous in both directions, and lets a repo un-ignore every derived deck PDF with one `.gitignore` line (`!**/*.pptx.pdf`) even under a blanket `*.pdf` ignore. **Keep deck extensions lowercase** — a case-sensitive repo would still ignore `.PPTX.pdf`; and a negation cannot reopen an ignored *parent directory*.

    **Freshness lives in a `.slide-sync.json` manifest at the repo root, which records the sha256 of the deck AND of each derivative — never mtimes, and never only a hash in the `.md` header.** Git does not preserve mtimes, so after a fresh clone every derivative looks newer than its source and an mtime check silently passes on stale files. A header hash in the `.md` is no better on its own: a `.pdf` cannot carry a provenance header and the non-`.pptx` formats have no `.md` at all, so `--md-only` (or a render that fails *after* the text was written) would leave a fresh hash sitting next to a stale PDF and the gate would call it in sync. **A manifest entry is written only after that derivative is successfully produced**, so a failed render leaves the gate red rather than green, and hashing each derivative also catches a truncated, hand-edited or replaced file. For the same reason `--check` always verifies the **full** derivative set: `--check --md-only` / `--check --pdf-only` are rejected rather than silently checking half of it.

    **The pre-commit gate validates the index, not the working tree, and reads filenames NUL-delimited.** A working-tree check passes while the commit itself carries only the deck — derivatives left unstaged — or carries a deck that differs from the one the derivatives were built from. And `git diff --cached --name-only` **quotes** any non-ASCII path: a deck named `… — Clear Metric Notation.pptx` arrives as `"… \342\200\224 … .pptx"`, whose trailing quote defeats a shell `grep '\.pptx$'`, so a filename-filtering hook silently never runs on exactly the decks Brando has. Renames matter too: `git mv` reports status `R`, which an `ACM`-only diff filter ignores. Hence `--check-staged` does the path handling in Python with `-z` and `--diff-filter=ACMRTDU` (including type changes and unresolved merges); Git inspection errors fail the check.

    **Renderer:** LibreOffice headless (`soffice --headless --convert-to pdf`, run against a scratch `-env:UserInstallation` profile so it never fights a running GUI instance, output staged to a temp file and moved into place) is the portable path — `brew install --cask libreoffice` on macOS, the distro package on Linux. The script's macOS Keynote/AppleScript fallback needs Automation permission granted interactively to the calling terminal (**System Settings → Privacy & Security → Automation**); without it AppleScript fails with `-600 Application isn't running`, which reads like a crash but is a permissions denial. **A deck is never edited through its derivatives** — edit the deck, re-run the syncer. Authoring a deck *as* text is a different workflow (Marp / `md` → `pptx`) and is not what this rule covers.

    **Setup in a new repo:** run `sync_slide_decks.py --install-hook`. It resolves the effective hooks directory via `git rev-parse --git-path hooks`, so `core.hooksPath` and linked worktrees (where `.git` is a *file*) work; it installs the logic as a standalone `slide-deck-sync-check` and, if a `pre-commit` hook already exists, **prints the one line to add rather than appending** — appending after an existing `exit 0` reports success while leaving the check unreachable. Add the `.gitignore` negations if the repo ignores `*.pdf`, and commit `.slide-sync.json`.

    **Why:** asked for by Brando 2026-09-08 — `experiments/23_thesis_plan_for_sanmi_and_azalia/(Final shown to Sanmi SK) - Thesis Plan Sept 4 2026 .pptx` was committed as a deck nobody could open, read, or review from the editor where the rest of the thesis lives, while `experiments/21_qual_exam_2026_slides/` had a *hand-exported* PDF and text dump that nothing kept in sync — the drift this rule removes. Defer local Rule 19 cleanup while the worker worktree is active, and record what remains; never switch another session's checkout or delete an active worktree. A cleanup failure is distinct from a failed merge and must not suppress the landing record. (4) **Email the landing** under the standing completion instruction in Trigger Rule 14, routed per Trigger Rule 26: one message per merged PR to `brando.science@gmail.com`, no carbon-copy (CC) recipients, subject `[<proj>] PR #<n> merged: <title>`, body = PR uniform resource locator (URL), TLDR, `diff --stat`, QA verdict, ledger and CKPT paths; for a failed task use `PR #<n> blocked: <title>` and the actual failure status, never `merged` -- sent by the worker itself with `uutils.emailing.send_email_smtp()` per Guideline 23, because an explicit email is a completion receipt independent of GitHub's notification settings. A follow-up that only publishes this landing record is part of the original completion: it needs deterministic documentation checks but no new completion email or further `LANDED` record about itself. ## Guidelines (best practices)

Follow these as conventions. They improve quality but are lower priority than Hard Rules and Trigger Rules.

14. **Just do it.** Follow direct instructions immediately. Do not draft when told to send. Do not ask for confirmation unless the action is truly destructive (e.g., force-push to main, deleting production data).
15. **Prefer references over full context loading.** Cite file paths as text (e.g., `~/agents-config/machine/mac.md`); load the file only when the task needs it. A "reference" here is a written path to a doc — not a symlink or memory address.
16. **Keep `agents-config` self-consistent.** When modifying this repo, ensure INDEX_RULES.md, README.md, and listed doc paths remain accurate.
17. **Use explicit anchored paths in prose doc references and commands.** Write `~/agents-config/INDEX_RULES.md` or `~/veribench/docs/agent-docs/INDEX.md`, never bare relative references like `docs/agent-docs/`. The user works across many repos and machines, so unanchored paths are ambiguous without context.
18. **Always use `ls -la` (not `ls`) when listing directories for keys, tokens, configs, or credentials.** Hidden (dot-prefixed) files are common for sensitive data — plain `ls` omits them. This applies to any directory likely to hold secrets (e.g., `~/keys/`, `~/.ssh/`, `~/.config/`).
19. **Use the strongest *appropriate* model tier for experiments — and always record the exact model ID.** Defer to Hard Rule 8 for which tier that is: reasoning-critical building and critical acceptance review use the flagship; ordinary review follows Hard Rule 8's explicit cross-company fallback; experiment *workloads* (eval backbone, agent-under-test, bulk generation) default to the regular thinking tier, escalating to the flagship when the workload demonstrably needs it or Brando asks for it. **An LLM judge that is part of the eval itself is a workload, not a review dispatch** — it follows the experiment tier and its exact model ID is reported alongside the results, however many times it is invoked. Whichever tier you use, state the exact pinned model ID in the results summary (e.g. `claude-sonnet-5`, `gpt-6-astra`) — a floating alias makes the run unreproducible, and an unrecorded downgrade undermines the paper's conclusions. **Superseded wording:** this guideline previously read "always use SOTA models for experiments", which contradicted Hard Rule 8's flagship-vs-regular split; Hard Rule 8 governs.
20. **Use Brando's email signature and voice.** When sending emails on Brando's behalf, apply the routing rule from Trigger Rule 26, append the signature from [`email-signature.md`](email-signature.md), and follow its voice rules: first person as Brando, concise, friendly, direct, with no third-person narration about Brando from Brando's own account.
21. **Check `~/keys/` for non-LLM credentials.** Before asking the user for non-LLM credentials, always check `~/keys/` first (`ls -la ~/keys/`). Common non-LLM files: `master_hf_token.txt` (HuggingFace), `brandos_wandb_key.txt` (W&B), `.brando90_github_token.txt` (GitHub), `push-pypi-all.txt` (PyPI), `gmail_app_password.txt` (Gmail SMTP). Load them with `cat ~/keys/<file>.txt` and set as env vars. **LLM-provider keys (`anthropic_*`, `openai_*`, `gemini_*`, `aristotle_*`) are excluded from this guideline** — per Hard Rule 9, agents may not load or use them; route LLM work through `clauded` / `codex` instead.
22. **No hardcoded Node/nvm versions in `.bashrc` PATH prepends.** `nvm.sh` (sourced in `.bashrc`) already puts the active node's bin first in PATH. A hardcoded line like `export PATH=".../.nvm/versions/node/v24.14.0/bin:$PATH"` will silently shadow a newer node after `nvm install`, causing `npm install -g <tool>` to update one install while the shell runs another — the "please update" loop bug. See [`machine/snap.md`](machine/snap.md) § "npm globals — update loop gotcha" for the diagnose/fix recipe.
23. **Email = send via uutils SMTP, MCP is fallback.** When told to send an email, use `uutils.emailing.send_email_smtp()` from `~/ultimate-utils/` (or `pip install ultimate-utils`) with `smtp_pass_file="~/keys/gmail_app_password.txt"`. This works on every SNAP node without browser auth. Only try the Gmail MCP tool if uutils is genuinely unavailable. Never create a draft when told to "send". Default from/CC per [`email-signature.md`](email-signature.md) and Trigger Rule 26: internal notifications go to `brando.science@gmail.com` with no CC; external emails CC `brando.science@gmail.com` for audit unless the user says otherwise. Contacts workflow: [`contacts.md`](contacts.md).
24. **Paper PDFs: see Trigger Rule 35.** Recompiling the PDF after a semantic `.tex` edit and keeping the compiled PDF committed is now a mandatory Trigger Rule, not a guideline.
