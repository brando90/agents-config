# Hosts: detailed rules

**Doc link:** <https://github.com/brando90/agents-config/blob/main/rules/hosts.md>

**TLDR:** Read the matching rule sections when routed here by `~/agents-config/INDEX_RULES.md`; this is on-demand policy, not startup reading. Existing rule numbers remain stable.

## Trigger Rule 38

38. **Run the SNAP cluster health check before dispatching a SNAP job.** _Trigger: you are about to start or dispatch an agent, experiment, benchmark, watcher, or setup command on a Stanford SNAP node._ Run `bash ~/agents-config/scripts/snap_health.sh --node <host>` first (or the no-argument all-node audit when choosing a host), and do not dispatch onto a node with an unresolved `FAIL` relevant to the job. `--smoke` is opt-in because it spends subscription tokens. Use one dedicated DFS clone per agent job; never repair a dirty shared working tree with stash/reset/checkout. See [`machine/snap.md`](../machine/snap.md) § "Cluster health" for canonical tool paths, LFS headroom, Slurm access, and the exact Git fetch refspec.

## Trigger Rule 46

46. **A remote worker lands its own work: branch, pull request (PR), requested quality assurance (QA), merge to `main` at once, email, and the dispatcher pulls.** _Trigger: a worker dispatched to a Stanford Network Analysis Project (SNAP) cluster node (or to any machine other than the one its dispatcher runs on) finishes a task, or a phase whose result belongs on `main`._ The worker never parks a finished result on a branch and never waits for the laptop. (1) **PR as the record:** it pushes its task branch (the Rule 42 name) and opens a PR with `gh pr create` whose body documents the work -- TLDR (too long; didn't read) summary, what changed and why, the verification commands with their exit codes, the QA verdict block when requested, the model identifiers (IDs) actually used (Hard Rule 8; both families for a gold-reference edit (benchmark reference data), Trigger Rule 43), and the paths of its `results.md` (Rule 37) and `CKPT_<task>.md` (`CKPT` means checkpoint; Rule 44). (2) **QA on the branch:** it runs the QA tier the runbook names, and only if Brando requested one (Hard Rule 3: QA is explicit opt-in; light = one review by the other model family, findings applied and verified deterministically; mega = Trigger Rule 10); with no tier named it runs and records the deterministic checks without mentioning QA; otherwise it records the verdict. (3) **Merge immediately, and only what was verified:** note the remote branch's current commit and fetch `origin/main`. Before each rebase, choose a worker-owned local backup-branch name; record that name, the old merge base (the shared ancestor commit of the task branch and fetched `main`), and the fetched `main` commit in the checkpoint. Commit the checkpoint update first so the working tree is clean, then save the current commit (the branch tip) with `git branch <backup-name> HEAD`. Rebase onto that fetched commit (replay the worker commits on the updated base), then compare the rebased content with the saved tip: review `git range-diff <old-base>..<saved-tip> <fetched-main>..HEAD` (the old and new sequences of commit changes) and `git diff <saved-tip> HEAD -- <task-owned-paths>`. Account for every dropped or changed patch: it must already be present upstream, or its replacement must preserve the intended result; restore accidental losses before proceeding. If the new patch series is empty, compare the saved changes directly with fetched `main` instead of treating an empty range or a failed comparison as success. A non-interactive conflict resolution can discard work even when rebase and compilation both exit 0; the comparison is a content review, not an exit-code gate. Re-run the deterministic checks (compile, tests, the targeted grep), then publish the rebased branch with a guarded update of that worker-owned branch only, `git push --force-with-lease=refs/heads/<task>:<previous-remote-commit> origin HEAD:refs/heads/<task>` (stop on rejection and inspect what changed on the remote; `main` is never force-updated). A head match pins the branch being merged, not the destination: `main` can move between the last check and the merge. Shrink that window rather than refusing to land -- rebase, re-verify and merge back to back, and if the merge is rejected because `main` advanced, repeat on the new base instead of merging a stale result. Enforced up-to-date-branch checks or a merge queue (GitHub's ordered merge process) close the window properly, so use and never bypass them where they exist; neither repository this rule governs has them (`agents-config` is unprotected, `veribench`'s plan offers no protection for a private repository, checked 2026-09-09), so there the sequence above IS the landing procedure -- note the residual window in the PR, do not leave the work unmerged. Merge only after deterministic verification succeeded and, when QA was requested, the review returned `VERDICT: PASS` or `FIXED` with `CRITICAL_ISSUES: 0`, binding the merge to the exact commit that was verified: `gh pr merge <number> --rebase --match-head-commit <verified-commit>` (`--squash` only when the branch is a string of intermediate work-in-progress commits with no useful individual history; run any repository-required local verification gate explicitly before merging; `gh pr merge` does not run a local Git pre-push hook, and setting a shell variable such as `VERIBENCH_LIGHT_QA_DONE=1` does not enforce server-side checks). A `FAIL` verdict, or any critical issue, means the PR stays open, the email says so, and the worker stops. Confirm `gh pr view <number> --json state,mergeCommit,url` says `MERGED` before reporting a landing; queue acceptance is not a completed merge. Check that state even if the merge command exits nonzero: `gh pr merge --delete-branch` can merge on GitHub, then fail to switch to local `main` because another worktree has it checked out, leaving the remote branch undeleted. In worktree-based runs, omit `--delete-branch` and perform cleanup separately after confirming the merge. For a remaining worker branch, use `git push --force-with-lease=refs/heads/<task>:<verified-commit> origin :refs/heads/<task>` so deletion is refused if another commit has appeared; inspect a rejection instead of deleting the newer work. Verify remote absence with `git ls-remote --exit-code --heads origin refs/heads/<task>` (exit 2 means no matching branch; a connection or authentication failure is not proof of deletion). Defer local Rule 19 cleanup while the worker worktree is active, and record what remains; never switch another session's checkout or delete an active worktree. A cleanup failure is distinct from a failed merge and must not suppress the landing record. (4) **Email the landing** under the standing completion instruction in Trigger Rule 14, routed per Trigger Rule 26: one message per merged PR to `brando.science@gmail.com`, no carbon-copy (CC) recipients, subject `[<proj>] PR #<n> merged: <title>`, body = PR uniform resource locator (URL), TLDR, `diff --stat`, QA verdict, ledger and CKPT paths; for a failed task use `PR #<n> blocked: <title>` and the actual failure status, never `merged` -- sent by the worker itself with `uutils.emailing.send_email_smtp()` per Guideline 23, because an explicit email is a completion receipt independent of GitHub's notification settings. The runbook must name a working absolute Python interpreter on the target: before dispatch, verify `<mailer-python> -c 'from uutils.emailing import send_email_smtp'` (an import check, which sends no mail); the source file's existence alone does not prove its dependencies are installed. If delivery fails, record the pending receipt and error, use Guideline 23's fallback when available, and still publish the confirmed merge signal in step (5); never report the email as sent without successful delivery. (5) **Signal the dispatcher through git**, the one channel that survives the laptop sleeping: after confirming the PR is merged, write into `CKPT_<task>.md` the line `LANDED <merged-commit-id> <pull-request-link> <timestamp>` (the checkpoint entry confirming the merge), refresh its `Last updated:` stamp and the completed phase, and set the ledger `Status: DONE` only when the whole task is finished (a landed phase of a longer campaign stays `RUNNING`); commit these record edits and publish them to `main` through the repository's permitted path (use a fresh record branch and a small follow-up documentation PR, or a direct docs-only push where the gate allows it). A follow-up that only publishes this landing record is part of the original completion: it needs deterministic documentation checks but no new completion email or further `LANDED` record about itself. The dispatcher (usually a Rule 45 master) starts a landing watch when it dispatches -- a loop over `gh pr list --state all --head "<task>" --json number,state,url`, retaining that PR number, then `gh pr view <number> --json state,mergeCommit,url` and `git fetch origin && git show "origin/main:<repo-relative CKPT path>"` for the `LANDED` line (the path inside `git show` is relative to the repository root, even when the runbook records an absolute path). Accept only a line matching this dispatch's exact merged PR URL and merged commit, not an older task or a search-title match -- and on the signal syncs its checkout with `git pull --rebase --autostash origin main`, but only in a checkout it owns exclusively, on local `main`, after confirming that every unpublished commit and uncommitted change there is its own (that pull rewrites the current branch and stashes whatever is in the tree, so another session's work could be rewritten or disturbed without any conflict); when the checkout is shared, it syncs an isolated worktree instead and reports the shared-checkout condition, and it inspects both the rebase result and the stash restoration before reporting success, preserving anything unresolved. Then it refreshes its CKPT and reports LANDED with the PR link.
    **Local catch-up schedule (Brando, 2026-09-11):** designate one scheduled coordinator per project to check remote progress and synchronize the user's named local checkout, normally every 30 minutes. Verify the schedule is enabled, record its identifier, owner, cadence, checkout paths, last successful run and actual local/remote commit identifiers in the master checkpoint, and perform an initial check. A local schedule requires the computer and app to be available; keep remote execution/recovery independent and reconcile missed changes on the next available run. Fetch and distinguish an open pull request from a verified main landing. To update a user-designated shared checkout, allow only a fast-forward on local `main` while holding an exclusive check/update/verification window agreed with its known writers (a lock alone is insufficient), with no tracked/staged changes or unpublished commits and no untracked/ignored path collisions. Pin the fetched main commit and merge only that inspected commit using `--ff-only --no-autostash --no-overwrite-ignore`; never automatically stash, reset, clean, rebase or switch it. If ownership, activity or file safety is uncertain, synchronize an owned isolated checkout and explicitly report that the checkout open in the editor is still behind. Do not create a pull request just to pull already-merged work. Give each invocation a concrete total deadline, per-operation timeouts and retry limit; prevent overlapping invocations before receipt or checkout writes, and bound lock acquisition. On timeout retain unknown/stale status and defer extended recovery to its owner. Apply the ownership check to reused isolated checkouts too. Report only meaningful progress, completion, changed blockers or sync failures; deduplicate unchanged checks. Pause this coordinator after all owned jobs are verified complete or explicitly canceled, required publications are confirmed and the designated checkout is current, or on explicit cancellation; preserve other manually paused schedules. At a rename, verify one canonical active experiment path and preserve untracked leftovers before moving them out of the active list; a fetch/pull alone does not remove them. This schedule complements Rule 48's remote recovery mechanism and does not itself prove that mechanism works.
    **Why:** Brando, 2026-09-08, after a queued instruction never reached a master session on a laptop at 0.1 gigabytes (GB) free and 11 GB swap with 21 agent panes (that session was taking about 45 minutes per tool call): "I always want the PRs to be pushed and then immediately merged smartly with main branch. Doing that makes the PR document what we did in the repo. It should be sending brando.science@gmail.com an email about the PRs ... something like that is what we should have for 'remote' snap workers. Once they are done and pushed to main and qa-ed -- the local say master agent that sent that job should be told it's done and do a git pull, smart merge/rebase if needed ... I don't want to deal with my computer freezing/being slow unresponsive again." A worker that lands its own work needs nothing from the laptop, so the laptop being asleep, frozen or on a train costs nothing; the PR is the durable record, the email is the push notification, and the git signal lets any later session, not only the one that dispatched, pick the landing up. The guarded push, the head-matched merge and the ownership check before the autostash pull (temporarily setting aside and restoring local edits) came from the Codex light-QA review of the first draft (2026-09-08): without them a rebase after publishing gets rejected or silently continues against the old remote branch, changes pushed after verification could ride into `main` under the verified verdict, and a shared checkout could have another session's commits rewritten without any conflict.
    **How to apply:** the dispatch prompt for a remote worker carries this landing protocol verbatim (Rule 36: a dispatched agent may never read this file) -- branch name, QA tier, merge mode, the email address, the ledger and CKPT paths -- and exports `GH_TOKEN` from `~/keys/.brando90_github_token.txt` so `gh` works unattended; the dispatcher records the landing watch in its Rule 45 CKPT section 4 so a successor can restart it; "smart merge" means rebase, deterministic re-verification, a guarded push of the task branch, then a head-matched rebase-merge, squash only for work-in-progress noise, never a forced update of `main`. Claude Code on a SNAP node authenticates with the long-lived `claude setup-token` token (`export CLAUDE_CODE_OAUTH_TOKEN=$(cat ~/keys/claude_code_oauth_token.txt)`; verified 2026-09-08; it has no Remote Control, so such a worker is inspected through its tmux persistent terminal session and its log), never with a copy of the laptop's interactive login: sharing copied interactive credentials across machines can invalidate another machine's login when the refresh credentials rotate (see the header of `scripts/push_claude_vals_creds.sh`), and the nodes' stored logins were already expired on 2026-09-08. If the token fails, select the next eligible executor from the master's verified Rule 48 plan and record its actual model/effort; do not automatically assign a flagship or change scientific pins. Review dispatches follow Hard Rule 8's separate bounded review procedure. Run the Rule 38 cluster health check before dispatching; the one-line `claude --model claude-sonnet-5 -p PONG` probe is the authentication check for a dispatch that is already authorized to spend, not a substitute for the health check. Probe on the regular tier: a flagship probe cannot tell a missing credential from a spent flagship allowance, and reports a working node as broken whenever the allowance is spent. Entitlement to the model the worker will actually run is proved by the worker starting, not by this probe. Run the worker from a private per-node copy of the `claude` binary with basename `claude-pinned` or `claude` (the executable names recognized by the launcher and board), in a worker-owned directory, with `DISABLE_AUTOUPDATER=1`; never overwrite a copy while a worker is using it (the shared distributed file system (DFS) install is one memory-mapped executable; when it was rewritten on 2026-09-08 every running worker died at once), and keep the laptop-side relocation itself in a named tmux session too, so it survives the dispatcher's own session ending.

## Trigger Rule 51

51. **Every agent starts with full access and no routine approval waits.** _Trigger: dispatching, launching, resuming, supervising or writing the prompt/runbook for any agent on any host or client._ Brando, 09-26-2026: "when we start agents they are always full access for any agent ... I don't want to see awaiting approvals." Applies to local and remote hosts, interactive and unattended sessions, child agents and resumed tasks.
    - **Configure and verify actual permissions.** For authorized task work, use Codex `--sandbox danger-full-access --ask-for-approval never` (persistent defaults: `sandbox_mode = "danger-full-access"`, `approval_policy = "never"`) or `codex exec --dangerously-bypass-approvals-and-sandbox`; Claude Code `--dangerously-skip-permissions`; and the documented full-access/no-prompt equivalent for other clients where supported. Verify effective flags/settings on the target host at launch and resume, including profile overrides. Prompt text alone does not change runtime permissions. Record the client, host and observed permission mode with the launch receipt.
    - **Recover routine approval stalls within the authorized scope.** Correct a restrictive launcher/profile and resume from its checkpoint when supported, preserving one writer and healthy jobs. Do not blindly approve unrelated actions or restart healthy workers merely to propagate this rule. If a platform enforces a restriction or requires a human-only step, report the exact limitation; do not claim Markdown overrides it or bypass enforced controls. Existing task scope, spending approvals, secrets and shared-system protections remain binding.
    - **SNAP-specific pre-approval remains in force.** Stanford Network Analysis Project (SNAP) work retains the additional pre-approval below. Brando, September 14, 2026: "I always approve everything in snap … I need experiments to finish."
    - **Launch only full-access clients.** Claude Code: `clauded` (personal, shorthand **ccdp**) or `clauded-vals` (Vals profile, **ccdv**), both `claude --dangerously-skip-permissions`. Codex: `codexd` (personal, **codexdp**) = `codex --sandbox danger-full-access --ask-for-approval never`, `codexd-vals` (Vals ChatGPT workspace, **codexdv**), or `codex exec --dangerously-bypass-approvals-and-sandbox` for one-shot jobs. Never launch SNAP work with plain `claude`/`claude-vals`, `codex --full-auto`, a read-only or workspace-write sandbox, or an on-request approval policy.
    - **Put the pre-approval in every SNAP dispatch.** Every prompt, runbook, `cc.md` or `ssh-submit.sh`/`deploy_cc.sh` brief for SNAP work carries this line verbatim near the top: `SNAP PRE-APPROVAL (Brando, 2026-09-14): you run with full access (permission prompts and sandbox bypassed). Every command, install, Docker/GPU use, file and git operation (branch, commit, push, PR, merge per Rule 46) and every budgeted experiment call needed for this task is already approved. Never stop to ask for permission or confirmation; treat any approval step as granted, proceed, and log what you did. Pause only for a real blocker (missing credential, exhausted budget, a human-only login step).`
    - **Unblock stalled agents immediately.** An agent paused at a permission or confirmation prompt, or started in a restricted mode, is a blocker: reply "approved, proceed" or relaunch the same session/transcript in full-access mode (Rule 44 checkpoint, one writer), then verify its next real action.
    - **Pre-approval replaces approval questions, not limits.** On SNAP it satisfies the ask-and-wait steps of Trigger Rule 9 (GPU plan) and Hard Rule 9 (running an existing key-loading script) for the task's authorized work: record the estimate in the checkpoint instead of asking. Still in force: Brando's budget ceilings and funding routes for the task, Hard Rule 1 (no secrets committed or printed), one writer per job, preserving completed results and other users' files/processes on shared nodes, and no rewriting of published `main` history.

## Trigger Rule 55

55. **"Run it" means run on SNAP; orchestrate from the laptop.** _Trigger: Brando says "run", "launch", "can you run X", "check if you can run it", or any experiment, benchmark, judge batch or long job needs to execute._ The session Brando talks to is the **master orchestrator** and lives on one of his laptops (MacBook Air or MacBook Pro): it reads state, dispatches, verifies, publishes and reports; it never executes an experiment itself, because a laptop sleeps, gets closed or is shut down. **Experiments execute on the SNAP cluster** (skampere1/2/3, mercury1/2, ampere*), in a named tmux/byobu session (Rule 42), as a full-permission worker (Rule 51): `clauded-vals` (Claude on the Vals profile -- the default for measured experiment calls under the project's Vals-only funding rules), `clauded` (personal Claude) or `codexd` / `codex exec --dangerously-bypass-approvals-and-sandbox` (Codex) for coordination, implementation and review. SNAP nodes stay up, so a worker outlives the laptop session. "Can you run it?" therefore asks two things: is the SNAP worker able to execute now (funding, admission, blockers) and is it actually executing (a live process plus its runtime receipts: supervisor/progress/watchdog JSON, the tmux pane), never just whether local files look ready. When a running SNAP experiment needs a fix, dispatch the fix to the worker session that owns it (type the brief into its tmux pane or its remote-control channel) rather than editing its runtime by hand from the laptop; do it yourself only when the owning worker is gone and Brando wants it now, and record what you did in that experiment's CKPT. **Why:** Brando, 09-15-2026, after an orchestrator on his MacBook Air asked whether "the experiment can run": "When they say you can run I guess I mean that you can run it in snap ... if this computer is shut down or whatever ... my servers are usually not shut down so ... experiments in snap are better." and "Usually I will do the master orchestrators here in my laptops ... And then the experiments will usually run Claude at Vals or Claude personal, all permissions, or codex, all permissions, in the cluster like snap."

## SNAP watcher reauth & reboot persistence (2026-04)

DFS job-queue watchers stay alive across the two failure modes (Kerberos/AFS ticket expiry every ~10 h, and node reboot) via two cron lines on each watcher node:
```
0 */4 * * * /dfs/scratch0/brando9/bin/krenew.sh                  # keytab kinit + aklog
@reboot     /dfs/scratch0/brando9/bin/start_watcher_at_reboot.sh # wait for DFS, krenew, relaunch
```
**No password ever leaves your Mac.** The reauth credential is `/dfs/scratch0/brando9/.keytab` (chmod 600), generated once interactively via `ktutil`; `kinit -kt` proves identity from the keytab without prompting. Automation (Claude Code, cron, Codex) only needs read access to the keytab file. If you change your Stanford password, regenerate the keytab — see [`init_no_passwords_snap_kinit.md`](../init_no_passwords_snap_kinit.md) and [`README.md`](../README.md) § "Keeping watchers alive".

inventory and reject SSH unless the user holds an allocation adopted by `pam_slurm_adopt`. Start

## SNAP Required Symlinks (every node)

Every SNAP node must have these symlinks in `$HOME` (LFS). Missing symlinks cause silent failures in tooling that assumes `~/...` paths resolve to DFS. `snap_setup.sh` and `machine/snap-init.md` create/verify them.

- `~/.bashrc` → `/dfs/scratch0/<user>/.bashrc`
- `~/agents-config` → `/dfs/scratch0/<user>/agents-config`
- `~/CLAUDE.md` → `~/agents-config/CLAUDE.md`
- `~/.codex/AGENTS.md` → `~/agents-config/AGENTS.md` (canonical Codex global entry point)
- `~/AGENTS.md` → `~/agents-config/AGENTS.md` (optional compatibility)
- `~/agents.md` → `~/agents-config/AGENTS.md` (legacy home-level compatibility)
- `~/.claude` → `/dfs/scratch0/<user>/.claude` (shared auth across nodes)
- `~/keys` → `/dfs/scratch0/<user>/keys`
- **`~/dfs` → `/dfs/scratch0/<user>`** (required by the DFS job queue watcher and any tooling that uses `~/dfs/...` paths; if `~/dfs` is a plain local directory instead of the symlink, `cp file ~/dfs/job_queue/pending/` succeeds locally on LFS and is invisible to the shared queue — see `workflows/remote-job-dispatch.md` § "Is any job of mine running?")
- Plus each project dir under `~/` (e.g. `~/veribench`) as a symlink to `/dfs/scratch0/<user>/<project>`
