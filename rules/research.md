## Trigger Rule 9

9. **GPU discipline: baseline → estimate → ask → verify → clean up.** _Trigger: about to launch a GPU job._ Before launching any experiment on a GPU, first run or reason from a 1-device baseline whenever practical. Report to the user: (a) estimated VRAM, (b) expected utilization pattern (compute-bound vs CPU/IO-bound), and (c) estimated duration, or explicitly state that the duration is unknown. If the workload appears mostly CPU or IO bound, or uses only brief compute bursts, say so clearly and suggest a smaller machine or a CPU-only node. Do not silently claim multiple devices. Present the per-device allocation plan and wait for user approval (on SNAP, Trigger Rule 51 pre-approves this: record the plan in the checkpoint and proceed). Hardware allows sharing, but PyTorch's caching allocator means memory footprints can spike unpredictably, causing OOM crashes for others. Furthermore, spreading low-utilization work across multiple devices hogs the system's PCIe bandwidth. Therefore, the etiquette rule is: a small memory footprint on one shared device is fine; spreading low-utilization work across multiple devices, or holding idle devices for long durations, must be avoided. **Hard Rule:** The agent MUST explicitly set `export CUDA_VISIBLE_DEVICES=<chosen_ids>` in the bash environment before executing any python script. Verify with `nvidia-smi` within a few minutes of launch. If utilization stays persistently low, report it to the user and suggest consolidating, fixing the input pipeline, or moving off the device. After completion, clean up orphaned processes and report the final state. See [`workflows/expts-and-results.md`](../workflows/expts-and-results.md) § Allocation Rules and § Post-Experiment Cleanup.

## Trigger Rule 20

20. **Verify Lean by actually compiling with the project's pinned toolchain — even in cloud sandboxes.** _Trigger: any request that requires Lean compilation / type-checking / proof verification (e.g., "check this proof", "does `imp ≡ functional` hold", "compile this file", "do the tests pass")._ (1) Find the pinned toolchain — `lean-toolchain` first (e.g., `~/veribench/veribench_dataset/lean_src/lean-toolchain`), else grep `.github/workflows/*.yml` for `leanprover/lean4:v` / `elan toolchain install`. (2) Install via elan and run `lake build` (or `lake env lean <file>`) for real: `curl https://elan.lean-lang.org/elan-init.sh -sSf | sh -s -- -y && export PATH="$HOME/.elan/bin:$PATH" && elan toolchain install <pinned> && elan default <pinned>`. (3) Report the actual `lake` output, not your guess. **Applies in Anthropic cloud / restricted sandboxes too** — install Lean and verify; never substitute "looks correct" for a real compile. **Why:** Brando uses Lean often; CI is the source of truth for the version that works; an unverified "this proves" claim is worse than admitting you didn't run it.

## Trigger Rule 28

28. **Save user-attached images / photos / scans into the relevant hypothesis or experiment folder's `assets/` folder.** _Trigger: the user attaches an image (photo of a handwritten note, screenshot, diagram, paper figure, whiteboard) in a prompt and asks to save / transcribe / file / keep it, or asks to create a research hypothesis / experiment / GitHub issue / prompt from the image._ (1) Identify the target hypothesis / experiment / project folder from context (the user usually names it, e.g. "experiment 02_", "hypothesis 00_", "the openclaw experiment", or the current repo if obvious). (2) Create `<that-folder>/assets/` if it doesn't already exist (`mkdir -p`). (3) Copy the original image there with a descriptive snake_case filename (`source_photo.jpg`, `summary_update_photo.jpg`, `handwritten_<topic>.jpg`, `whiteboard_<date>.png`, `screenshot_<feature>.png`) — not the original opaque UUID upload name. (4) Before writing or finalizing `pre_prompt.md`, `issue.md`, transcriptions, plans, or README entries from the image, add a provenance line pointing to the saved `assets/...` file and, when available, the original upload path. (5) For research hypotheses, include a compact summary block near the top with: one-sentence **Goal**, **Confidence** (percentage or low/medium/high), **Importance** (0-10 or low/medium/high), and any **Key uncertainty**. (6) If a transcription is requested, save it as a sibling `.md` next to the image, same basename, with provenance, the original image path, and a `**TLDR:**` header per Trigger Rule 16. (7) Commit both the image and the transcription / prompt / issue file as part of normal repo workflow. **Why:** the original upload path under `~/.claude/uploads/<uuid>/`, `/tmp/codex-remote-attachments/<uuid>/`, or similar is ephemeral and opaque — it disappears across sessions and machines, and the UUID filename tells future Brando (and future agents) nothing about what's in it. Co-locating the original image with the hypothesis / experiment keeps the artifact discoverable via `git log` / `ls`, lets readers cross-reference the transcription with the original handwriting / pixels, and avoids one-off "images" or "scratch" top-level folders that erode over time. **How to apply:** default to `assets/` (singular precedent: `experiments/01_toy_ebm_training/assets/`). If the user names a different subfolder (e.g. `figures/`, `notes/`), honor that instead. If the target folder doesn't exist yet but the task is to create it, create the folder and its `assets/` subfolder together; if the target is genuinely ambiguous, ask. If the image is a screenshot of a *third-party* paper / figure, also flag it in the transcription so it's clear what's original vs. cited. Mirror briefly in [`workflows/expts-and-results.md`](../workflows/expts-and-results.md) so it's discoverable from the experiment workflow doc.

## Trigger Rule 37

37. **A long or dispatched run keeps `results.md` live in the repo — not a report at the end.** _Trigger: you start any run that will take more than a few minutes, or you dispatch one to another agent / a cluster node (a benchmark sweep, a labelling pass, a multi-phase experiment, a build campaign)._ Create the experiment's root `results.md` **at launch**, with `**Status:** RUNNING (started <ts>)`, and **update it every time a meaningful result lands** — a phase completing, a gate producing counts, a tier table, a score — then commit and push that update. Each revision carries `**Last updated:** <ts>`, a phase table (`DONE` / `IN PROGRESS` / `PENDING`) and the numbers obtained so far, and it closes with a `**TLDR-end:**` carrying Hard Rule 4's `[proj: task]` tag, with no opening `**TLDR-start:**` or `**TLDR:**` (end-only, Brando 09-22-2026; this overrides Rule 16's opening summary). **A progress file that lives only on the cluster does not count:** a `PROGRESS.md` under `/dfs/...` or `/lfs/...` is invisible to Brando, who then cannot answer "what is the state of this thing?" without opening an ssh session — which is exactly the situation he is dispatching work to avoid. **When you dispatch to another agent, put this obligation verbatim in the prompt** (per Rule 36, a dispatched agent may never read this file), including where the repo `results.md` lives and that it must be committed as the run proceeds; and if the dispatched agent cannot push (no credentials, a protected branch, a shared dirty tree), the *dispatching* session owns mirroring the node's progress into the repo at each check-in. **Experiment-folder Markdown (`.md`) reports are the primary and sufficient reporting deliverable** (Brando, 09-20-2026). Weights & Biases (W&B) logging, dashboards, and Reports are optional and run only when the user explicitly requests them; W&B credentials or dashboard publication are never prerequisites for ordinary experiment progress, completion, notifications, or handoff. Preserve historical report links and receipts. For multi-stage metrics, also publish each example's available components, its combined score when defined and complete, running aggregates with their row counts, and the blocked stage; follow [Streaming multi-stage metrics](../workflows/expts-and-results.md#streaming-multi-stage-metrics). **Why:** stated by Brando 2026-09-03 — experiment 74 had been running for over an hour on a SNAP node and had already produced real numbers (878/896 gold files compiling, 18 failures, a 10/539/347 easy/medium/hard tiering) while the repo showed nothing at all: "74_ doesn't have a results .md so I'm confused what the state of the thing is. The results should always have a tldr at the end too and be continually updated as meaningful results are obtained." The end-of-run report is not a substitute; it is the archival record, and `results.md` is the live one. See [`workflows/expts-and-results.md`](../workflows/expts-and-results.md) § Results Storage.

**Results report filenames (Brando, 09-15-2026).** Name reader-facing results reports `RESULTS_<concise_topic>.md`, for example `RESULTS_judge_validation.md` or `RESULTS_theorem_coverage.md`. Use a short, descriptive lowercase topic with underscores; keep the report in its canonical experiment or relevant phase folder and link it from the experiment README and live `results.md`. This names the readable report, not raw data or the mandatory live `results.md` ledger. Follow [Results Storage](../workflows/expts-and-results.md#results-storage) for versioned snapshots, provenance and safe renames.

## Trigger Rule 39

39. **Experiment folders: name them after the setup, and keep the folder list to ACTIVE work.** _Trigger: starting, continuing, finishing, or renaming an experiment in any repo._ Two rules, both from Brando on 2026-09-04 ("I only have active or important expts on the experiments folder"; "we should be more precise in the expt names ... the folder should say what the setup is"). **(a) The name states the setup** — what is being searched or measured, and over what split — not a vague noun phrase; six weeks later nobody remembers what "main table" or "heldout selection" meant. `76_judge_config_search_train_val_test` and `78_prover_checked_coverage_vs_llm_judge` are the shape to copy. **User-assigned labels (September 11):** when Brando identifies workstreams with labels such as `E1` or `S1`, use `<NN>_<LABEL>_<descriptive_setup>` and define the label in the project experiment index. Keep one canonical root per number; follow an exact user-specified name, including pause-marker order; otherwise place a requested pause marker after the label, such as `<NN>_<LABEL>_PAUSED_<descriptive_setup>`. Do not invent labels for other work or retrospectively renumber archives. Coordinate concurrent owners, update prospective path consumers, and verify preserved contents; frozen evidence and running private checkout paths retain their recorded identities. **(b) Numbered homes directly under `experiments/` hold core work; `experiments/ideas/` holds optional research.** A strand with a final verdict and no live dependency moves to `experiments/archive/` with a one-sentence outcome row in `experiments/archive/README.md`; archiving keeps it readable in-repo, it is not deletion. **Archive when done (Brando, 09-28-2026: "archive means done basically, not active"):** the agent that records an experiment's final verdict (a `results.md` or checkpoint saying COMPLETE, DONE or STOPPED) moves the folder to the archive in that same commit, unless its README names the live dependency that keeps it active. **Before archiving, grep the source tree (`py_src/`, `scripts/`, `src/`, tests, CI, the paper) for the folder path: a folder that holds live infrastructure is PROMOTED to a first-class home, never archived** — that is how VeriBench's expt 35 became `vb_harbor/` and expt 38 became `scripts/scsc/`. Keep rename history (old → new) in the archive index only, never in a rules file or a project CLAUDE.md, so that grepping live files for a stale folder name stays a real check instead of hitting its own changelog.

**Keep an experiment’s data and code together (Brando, 09-19-2026).** The default home for all experiment-specific material is that experiment’s canonical folder: source snapshots/archives, raw and derived data, candidate datasets, code, prompts, configurations, manifests, logs, results and documentation. Use sensible subfolders and version folders there; being importable code or a generated dataset does not by itself justify moving it into repo-level `src/`, `scripts/`, `data/` or a separate checkout. For example, VeriSoftBench (VSB) → VeriBench V2 (VBV2) construction belongs under `experiments/91_lean_to_python_hopefully_unsaturated_vb/`. Promote only shared code used by multiple experiments or production or an intentionally released dataset to its established project home, and link that dependency from the experiment README instead of duplicating it. If size, remote execution, licensing or access restrictions require external storage, keep a manifest/pointer in the experiment with the exact location, reason, version/hash where practical and retrieval command; prefer the same experiment-relative layout on the execution host. Keep private data ignored and credentials in their existing secret store: keeping files together does not authorize committing or publishing them. Honor user moves and existing canonical homes; coordinate relocations, update live references and preserve frozen receipts and running checkouts. Details: [keep data and code together](../workflows/expts-and-results.md#keep-data-and-code-together).

**New experiments and continuations.** Unless the optional-ideas exception below applies, a newly authorized distinct experiment defaults to a checked-available numbered, setup-descriptive home directly under `experiments/`, with a project experiment-index row. Inspect existing, archived and reserved work plus active branches/owners before allocating; honor exact user numbers, labels and names without silently repurposing an occupied number. Continue matching work in its existing canonical home instead of creating a duplicate. Automatically follow the repository's existing experiment documentation conventions without reminders: concise goal/hypothesis and decision criterion, inputs/protocol/runbook, live `results.md` at launch, and a dated resumable checkpoint for qualifying runs (Rules 37/44). Use [the experiment workflow](../workflows/expts-and-results.md#starting-or-continuing-an-experiment); ordinary edits, short lookups and research conversations alone do not require experiment folders.

**Optional ideas (Brando, September 12).** Put research whose priority or paper inclusion is uncertain under `experiments/ideas/<descriptive_setup>/`, indexed in `experiments/ideas/README.md`. Honor user-assigned identifiers such as `IDEA_00` and exact paths. Distinguish execution status (`DEFERRED — NOT RUN`, `PLANNED`, `RUNNING`, `BLOCKED`, `DONE`) from paper-inclusion status (`UNDECIDED`, `INCLUDE`, `OMIT`). Recording an idea alone does not launch it; an explicit request to run it authorizes execution in its existing ideas home without mandatory promotion. A deferred proposal needs only a short README with a hypothesis, motivation/source links, priority/reason, key uncertainty, minimal comparison and revisit condition. Once execution starts, all ordinary experiment, live-results, checkpoint, review, resource, dispatch and publication requirements apply; `ideas/` is not an exemption. Check existing workstreams before creating duplicate work. If promoted to core work, coordinate the move, preserve provenance and update indexes/links; never move a running private checkout. Keep completed optional work while a live inclusion decision depends on it; otherwise use the project's established archive. Details: [optional research ideas](../workflows/expts-and-results.md#optional-research-ideas).

## Trigger Rule 49

49. **Research repo layout: four buckets at the root, everything else is a stray.** _Trigger: creating a top-level directory or file in a research repo, onboarding a repo, or being asked to tidy/simplify a repo root._ Brando, 2026-09-12, on a `~/veribench` root that had grown to 24 top-level entries: *"I prefer to keep things simple. Usually I only really need 1. experiments folder with all my experiments, results etc 2. latex file for my papers/notes 3. src for the main code and prompts."* The root holds at most **four buckets** — `experiments/` (every experiment, its scripts, results and checkpoints; naming and archiving inside it are Trigger Rule 39), `paper_latex_and_notes/` (anything a human reads: papers, notes, blog, talks, paper-support scripts — one bucket, because notes become papers), `src/` (shared production/library code **and** shared prompts: `src/py_src/`, `src/prompts/`, `src/scripts/`; experiment-specific code/data/prompts remain together in the experiment home under Rule 39, even when importable), and **only if the repo ships a data artifact** one data bucket (`<name>_dataset/` or `data/`, kept at the root because it is the product, not source) — plus an allowlist of root files: `README.md`, `CLAUDE.md`/`AGENTS.md`, `LICENSE`, one package config, one lockfile, one setup script, `tests/` (pytest convention wins over bucket purity), and dotfiles.
    - **Route every stray, never grow a fifth bucket.** Unrelated to the repo's purpose (coursework, another project) ⇒ **out of the repo** — copy it somewhere safe *first*, then `git rm`, since `git rm` preserves nothing but history. Zero inbound `git grep` references is supporting evidence, never sufficient on its own: confirm the purpose mismatch, and check for consumers git-grep cannot see (CI, other repos, a person's muscle memory). Generated or ephemeral (`tmp/`, `_build/`, caches, a lone `*_cache.json`) ⇒ `.gitignore`, never a directory. Otherwise: a run/result/ledger ⇒ `experiments/`; prose a human reads ⇒ `paper_latex_and_notes/`; code, prompts or shared tooling ⇒ `src/`; the released artifact ⇒ the data bucket. Unsure ⇒ `experiments/`; promoting out of it later is cheap, a new root directory is not. Never create a root directory for one file, never leave an empty one, and when Rule 39 promotes live infrastructure out of `experiments/`, promote it **into `src/`** rather than onto the root.
    - **A reorg is a mass rename: inventory in-flight work before moving anything.** Run `git worktree list`, `gh pr list`, and `git diff --name-only origin/main...<branch> | cut -d/ -f1` over every unmerged branch. A branch cut *before* a rename still carries the old paths. Git's rename detection follows *edits* to a renamed file into its new home, but a branch that **adds** a file under the old directory re-creates that directory on merge, and every stale path string in prose, config, CI and runbooks merges back verbatim — so the tidy root regrows one merge at a time. Stage accordingly: move what nothing in flight touches now, defer the rest to an announced flag day once the open PRs land.
    - **Move with `git mv`; update live references only.** `git mv` preserves rename detection (`git log --follow`, `git blame`); confirm with `git diff --cached -M --name-status`, which prints `R100 old new` (`--stat` shows `{old => new}/f` instead, never the `R` code). Update packaging, CI, hooks, `CLAUDE.md`, imports and anything still run — but never rewrite frozen manifests, recorded results or archived READMEs, which state what the path *was* at run time. Re-check the three things a rename **silently** disarms. (i) Hook and CI path globs: a `case`-style matcher such as `*/paper_latex/*` stops matching after the rename, falls through to its no-op branch and exits 0, so the hook never errors — it just never runs again; fire it once to prove it still works. (ii) Implicit `sys.path`: a package importable only because it sat at the repo root breaks under `src/` — add `pythonpath` in the same commit and run the tests. (iii) Relative paths inside the moved files, which all shift by the depth you moved them. Leave the dated old→new map in the repo's `LAYOUT.md` — never in a rules file and never in a project `CLAUDE.md`, which Rule 39 reserves so that grepping those files for a stale name stays a real check. Full procedure, canonical tree and audit command: [research repo layout](../workflows/research-repo-layout.md).

## Trigger Rule 50

50. **Choose the consequential uncertainty, then shorten the path to evidence.** _Trigger: uncertain research, design or experiment work._ Apply this by default, without a reminder. **Vectoring** means choosing the failure-critical uncertain assumption that can be attacked now; **research velocity** means the rate of reducing that chosen uncertainty. Based on Brando's [Vectoring: Attack the Biggest Uncertainty First](https://brando90.github.io/brandomiranda/2026/04/16/vectoring-in-research.html) and [Velocity in Research](https://brando90.github.io/brandomiranda/2026/04/16/velocity-in-research.html):
    - Name the central assumption whose failure would undermine the objective, and the next decision the evidence must inform. Separate this core question from peripheral implementation or polish.
    - Choose the cheapest sufficient, falsifiable test that distinguishes the relevant possibilities. Reuse existing evidence/code; reduce scope or fidelity, use a subset, manual check or simulation when it still answers that question. Build only the infrastructure needed for a trustworthy test.
    - Before measuring, record what evidence supports continuing, redirecting or stopping, plus a justified bound on the test's scope, time or cost. Keep inconclusive evidence explicit; do not force a verdict or impose an arbitrary universal deadline. Use the existing experiment record/protocol when applicable, not a new planning bureaucracy or permission checkpoint.
    - Judge progress by useful uncertainty reduced, not code volume, infrastructure or positive results. A decisive negative finding is progress. As evidence arrives, revisit the chosen uncertainty and next test; redirect on evidence, not frustration. Document deviations and new iterations without rewriting a locked protocol or frozen results; follow the `PROTOCOL.md` contract in [the experiment workflow](../workflows/expts-and-results.md).
    - Speed never waives correctness, valid measurement, safety, required review, permissions or budget controls. These terms guide agent planning; preserve Rules 23–24 by using plain-language equivalents in reader-facing prose. Follow the linked posts when more context or examples are needed.

## Trigger Rule 61

61. **Run every solver/agent evaluation through its full declared set without premature orchestration stops.** _Trigger: planning, dispatching, continuing or reporting any solver/agent evaluation, for any model, provider, harness or project._ Read and enforce [the uninterrupted evaluation contract](../workflows/expts-and-results.md#uninterrupted-evaluation-of-the-full-declared-set). Freeze all files/tasks/questions and every model × task × seed/repetition cell before measurement; preflight nested timeouts, resources and finalization for the whole set; provide persistent execution and monitoring. Every initial and continuation prompt carries the strict [solver completion reminder](../workflows/expts-and-results.md#solver-completion-reminder). Let healthy work follow the fixed bounded procedure, verify actual final artifacts/logs/compiler or other checks, and reconcile every cell. A smoke pass or one clean task is not a completed evaluation. Keep failures, missing outputs and interrupted rows in the full denominator; distinguish clean procedure completion, budget-exhausted incomplete generation and infrastructure interruption from correctness. Preserve prior evidence/accounting and freeze unplanned recovery as a separate prospective condition without score-based cherry-picking, unlimited retries or silent model/settings changes. Explicit cancellation and genuine limits still apply; this rule promises neither impossible immunity from outages nor nonzero scores. It complements Rules 39/44/48/55/58 and constrains executor-recovery advice whenever the agent itself is being measured. **Why:** Brando, 09-20-2026, requires uninterrupted evaluation of all files/tasks/questions in the entire declared data-point set for every solver/agent, with a strict reminder to finish the assigned task.

In the reply give the clickable path to the new folder, the copy-ready sentence and the full Part 1 text itself (always both, file and reply; Brando, 10-02-2026), commit and push the folder (Trigger Rule 8), and edit his Google Docs only when he asks (Trigger Rule 56): the doc is his, the repo folder is the agents' record. **Why:** Brando, 10-02-2026: "where did you put the weekly update?" after an agent left the first filled-in update in a session scratchpad that was cleared overnight; he wants updates in a dated folder "so that the most recent appears at the top as time passes, in the cursor work tree" and the path given "clearly so I can click to it".

## Guideline Rule 19

19. **Use the strongest *appropriate* model tier for experiments — and always record the exact model ID.** Defer to Hard Rule 8 for which tier that is: reasoning-critical building and critical acceptance review use the flagship; ordinary review follows Hard Rule 8's explicit cross-company fallback; experiment *workloads* (eval backbone, agent-under-test, bulk generation) default to the regular thinking tier, escalating to the flagship when the workload demonstrably needs it or Brando asks for it. **An LLM judge that is part of the eval itself is a workload, not a review dispatch** — it follows the experiment tier and its exact model ID is reported alongside the results, however many times it is invoked. Whichever tier you use, state the exact pinned model ID in the results summary (e.g. `claude-sonnet-5`, `gpt-6-astra`) — a floating alias makes the run unreproducible, and an unrecorded downgrade undermines the paper's conclusions. **Superseded wording:** this guideline previously read "always use SOTA models for experiments", which contradicted Hard Rule 8's flagship-vs-regular split; Hard Rule 8 governs.
