## Hard Rule 4

4. **TLDR at the end.** Every response must end with a `**TLDR-end:**` line — 1–2 sentences — written last, from the actual response content, so it reflects any conclusion that changed along the way. Do not open responses with a `**TLDR-start:**` line; Brando retired the opening TLDR on 2026-09-14. **Project tag:** prefix the TLDR with a square-bracket tag in the format `[proj: task]` — **project first**, then the current task; if there is no clear task yet, project only: `[proj]`. Use a concise/abbreviated project name (e.g. `vb` for veribench, `beyond-scale`) — e.g. `**TLDR-end:** [vb: leap-gemini-key] …` — so Brando can tell which project/conversation a response belongs to from the TLDR alone (he reviews many per day and otherwise cannot place them). Lean on the project as the anchor. Keep the whole tag short, and outside the 1–2 sentence budget.

   **Core-work reminder (Brando, 10-05-2026).** "Remind me what the most relevant/recent task you are doing (like important core experiment I mean, not small things like 'test arg', more like 'generating outputs with FMs for human judgements') … at the very least in the tldrs." The task part of the tag names the core experiment or deliverable the conversation is pursuing (what Brando would write in his weekly document), not the current micro-step; it changes only when the core work changes. A sub-step may follow `›`, for example `[vb: expt106 fake-human panel, leave-one-agent-out judge test › Argon smoke test]`. The TLDR's first clause restates that core work in plain words before the step's result, so a reader who sees only the TLDR knows which real experiment is running. Applies to all agents (Claude Code, Codex, etc.). No exceptions.

   **Copy-ready weekly-update sentence (Brando, 09-24-2026).** For substantial research or experiment updates, open with one plain, self-contained sentence that Brando can paste directly into his weekly Google Doc: aim for one rendered line, two at most, matching the brevity of the approved example below. Include the experiment, essential setup and current result/status; omit secondary settings and operational details. Use current verified facts, and keep pending results explicit. This opening sentence has no heading or `TLDR-start` label; retain the closing `TLDR-end` and Snapshot protocol.

   Approved example: Experiment 95: 896 VeriBench tasks via Valkyrie; Terminus2 + GPT-6 Luna solver, GPT-6 Sol judge (both high reasoning); results pending.

   **Task titles match copy-ready summaries (Brando, 09-25-2026).** Name each agent/chat/task with the same self-contained, one-sentence summary used in Brando's tracking document: project or experiment identifier, concrete scope/setup (including solver/judge models and effort when relevant), and latest verified outcome or unresolved goal. Keep the identifier first so truncated sidebars remain recognizable. Prefer the full sentence when supported; if a hard title limit applies, preserve identifier, distinguishing setup and status, and keep the full sentence in the task's first summary/checkpoint. Refresh the title when scope or material status changes; never imply the research goal is achieved merely because a run ended. Do not rename unrelated tasks speculatively. Agents own their title updates using their own evidence. Propagate rule changes with one brief notice at the next safe boundary: no worker interruption/restart, repeated acknowledgments, or changes to experiment settings/schedulers.

   Approved title example: Experiment 95: 896 VeriBench tasks via Valkyrie; Terminus2 + GPT-6 Luna solver, GPT-6 Sol judge (both high reasoning); 881 compiled, judging failed, saturation unresolved.

**Compact results entries (Brando, 10-15-2026).** For a task-list result, weekly-update item or chat result summary, use **1–2 sentences plus two links**: state the finding with its decisive numbers and scope, then the material limitation or consequence. Finish with `Table:` and verified links labeled `.md` and `gdoc`. Keep full methods, uncertainty, factor tables and execution history in the linked reports. Do not expand a short result entry into the full-report template. If a requested link is unavailable, say so briefly; never invent one. See [the exact format](../workflows/statistics-reporting.md#compact-results-entry).

**Copy-ready collaborator message (Brando, 10-16-2026).** Whenever giving Brando research results, also include one **1–2 sentence message in Brando’s voice** that he can copy to Sanmi or the intended collaborator. Label it `Copy-ready message` outside the draft text. Use natural first-person wording where appropriate, scientific but easy to read; improve clarity without making his voice stiff or dense. Infer the audience from the conversation rather than always addressing Sanmi. State the main finding, enough scope and decisive numbers to interpret it, and the caveat or consequence that changes the takeaway. Distinguish measured results from hypotheses; preserve uncertainty and avoid causal overclaims.

Give one draft by default, not several alternatives. Keep internal paths, operational details, full statistical tables and chat-only closing blocks outside the copied message; relevant report links may accompany it. This message supplements the result summary and linked Markdown/Google reports, and is distinct from the opening weekly-update status sentence. It applies to research results, not routine administrative updates. Drafting does not authorize sending a message.

## Hard Rule 5

5. **Verification snapshot after TLDR-end.** Immediately after `TLDR-end`, append a `**Snapshot:**` block — a small, concrete, inspectable sample of the actual artifacts the task produced, so the user can visually confirm the work was really done without re-running commands. Target ~5–15 lines total; hard cap 25. Pick the *smallest representative sample of real output*, not a restatement of the TLDR and not an abstract description. Examples: 3–5 rows of a generated table/dict, first/last lines of a written file plus its path and size, URLs of pushed commits/PRs, the diff's `--stat` summary, a directory listing of new files, the exact command executed and its first few lines of output. For intangible tasks (a decision, explanation, refusal) include a one-line before/after or a cited file path + line range. If there is genuinely nothing to show, write `**Snapshot:** _(nothing to show — [brief reason])_` — do not silently omit. Applies to all agents.

## Hard Rule 10

10. **Expand every acronym and define every piece of jargon on FIRST USE, in every response.** Applies to ordinary chat replies, not just to papers and reader-facing prose. The first time an abbreviation, initialism, or project-specific term appears in a response, write it out and say what it means in one short clause: `TBH (to be honest)`, `SCSC (Smooth Conjunctive Score for Code verification)`, `IC_pp (fraction of the agent's stated theorems it actually proved)`, `the fresh re-run` (rather than an in-house label like "Arm 2" that means nothing outside the experiment folder). Casual abbreviations count: `tbh`, `iirc`, `afaict`, `wrt`, `ETA`, `EOD`. So do metric symbols, factor names, experiment-internal vocabulary, file/label identifiers, and any term whose meaning depends on a document the reader is not currently looking at. Use the expansion once, then the short form freely for the rest of that response; re-expand in the next response, since Brando may be reading it on its own. **The trap this closes:** an agent reads an experiment README or a results summary, absorbs its private vocabulary, and then writes as if that vocabulary were shared -- but Brando is reading the reply, not the file the agent just read. **Why:** stated by Brando 2026-09-02 after a reply built an entire analysis on the in-house labels "Arm 1" / "Arm 2" without ever saying what they meant, leaving him to ask whether it meant the ARM hardware architecture. **Borrowed metaphors are jargon too:** "arm" there was the clinical-trial sense (one branch of an experiment), which is useless to a reader who is not running clinical trials -- the fix was not to define it but to rename it to what it actually was, a rescore of old runs versus a fresh re-run: "tell me what acronyms mean. I don't know what you're talking about" and "otherwise I don't know what the fuck you're talking about in your responses agents!" An unexplained acronym silently transfers the agent's work onto the reader. **Distinct from Trigger Rules 23 and 24**, which govern jargon in *reader-facing prose* (papers, blog posts); this Hard Rule governs every response the agent writes, to anyone, including Brando.

    **Codes carry a gloss (Brando, 10-13-2026).** In anything Brando reads (chat, weekly-update text, to-do lines, email), a code-like name may lead and may be bold, but on its first use in a message or section it is followed by a short parenthetical saying what it is, the way agent task titles do: `**V21-008** (the SampCert task, first candidate for the private V2.1 set)`, `**1A** (raters qualify on the first warm-up task only)`, `**T01** (Rylan)`, `**C17** (the amendment that fixed that rule)`. Later mentions in the same message may use the bare bold code; a plain-words name with the code in parentheses is equally fine. What is never fine is a bare code with no gloss anywhere in the message. Agent-to-agent records (checkpoints, ledgers, commit messages) may keep bare codes. **Why:** Brando, 10-13-2026, reading "102 set-N round: 1A, 2A, 3A ... V21-008 D1-D3 ... V008-01 D1-D4": "too many acronyms ... for me as a human it's difficult to read"; then, on an all-plain-language reply: "We can use both. The bolded acronym like names is nice. Maybe it just needs a parenthesis with a small description or something? Like the agent tasks titles sort of have."

## Hard Rule 11

11. **Show measured numbers alongside verdicts.** In every response or report, accompany pass/fail, accepted/rejected, threshold outcomes and qualitative judgments with the actual measured numerical results that support them; a verdict such as "none passed" alone hides how good the results are. Give clear metric names, units or scales, sample counts/denominators, the data split or phase, and uncertainty when available. For correlation analyses, report Pearson, Spearman and Kendall individually when available. When a score's value is itself interpreted (a level, threshold, "saturated" or a mapped scale), add one absolute-agreement statistic, such as ICC(A,1) or mean absolute error with mean bias, because correlations cannot show a constant offset; define bias with its sign every time, as the mean of (judge or model score minus the human or reference score), so a positive bias means the judge is lenient, and give the two means it comes from (Brando, 10-02-2026). Uncertainty, both always: give a 95% interval for every headline estimate, saying what was resampled (tasks, items, repeats) and what the interval does not cover, and add a p-value whenever a verdict is read from the number, against a named null (a zero difference, or the pre-declared threshold such as a 0.45 agreement gate or a 0.8 saturation line), naming the test; do not report p-values against "correlation is zero", which are uninformative, and write every interval as x [lo, hi] followed by p-val=Z naming the test, or p-val=n/a when no test was run (Brando, 10-02-2026). Full results reports follow the detailed example in [`workflows/statistics-reporting.md`](../workflows/statistics-reporting.md#detailed-report-example-brando-10-02-2026): hypothesis as a question plus the metric, instrument with train/val/test agreement, results per system, a verdict bullet against the pre-declared threshold, a next step. For repeated scoring, report standard deviations and repetition counts, distinguishing variability across raw repeated scores from repeatability of aggregated scores (state what was aggregated and how). Compute these from data the experiment already has: this rule never requires extra runs, seeds, model calls or human labels, and a statistic the data cannot support is reported as "single run" or unavailable. Prefer cheap, honest reuse of that data to estimate uncertainty and variance, such as a bootstrap or permutation test over the independent unit (tasks or seeds, not correlated items within them) or statistics over repeats already made, and name the method. Validating a judge or proxy against human labels follows the [judge-human agreement checklist](../workflows/statistics-reporting.md#judge-human-agreement-checklist); both tiers, with reasons, are in [`workflows/statistics-reporting.md`](../workflows/statistics-reporting.md). "Raw numbers" means actual measured values, including useful summaries, not a dump of every observation. Mark missing metrics **unavailable** or **not measured**, never invent them. Show thresholds as secondary context and identify their source: user-chosen, protocol-defined or agent-suggested. A promising starting point is not an acceptance gate; this reporting rule never changes scientific protocols, results, thresholds or scoring. **Why:** Brando, 09-15-2026, asked to see the numbers behind judge-validation verdicts, not just whether they cleared a threshold. On 09-30-2026 a VeriBench judge with Pearson 0.86 still scored 0.18 above expert raters on average, which correlations alone could not show; Brando then asked that the rule stay cheap and general across training, reinforcement-learning and judge experiments.

**Presentation exception for compact result entries (10-15-2026).** Hard Rule 11 still governs the underlying evidence. In the 1–2 sentence format above, give the decisive values and denominator/scope, and put the full confidence intervals, resampling unit, p-value or `p-val=n/a`, mean bias, repeated-score variability and provenance in the two linked reports. Keep uncertainty in the short entry whenever omitting it would change the verdict. This is a brevity rule, not permission to imply an unmeasured result or unsupported generalization.

## Trigger Rule 16

16. **Document headers: title, clickable document address, then summary.** _Trigger: you create a new document or substantially rewrite one (any `.md`, `.txt`, `.rst`; design docs, plans, READMEs, reports, summaries, postmortems, eval writeups)._ The first non-blank line of the file MUST be a `# Title` heading describing the doc's purpose, followed by a `**TLDR:**` block of 1–2 sentences summarizing the document (after the document link when applicable). Why: Brando reviews many auto-generated docs per day and cannot read every body — a missing or weak TLDR makes the work unverifiable in practice ("otherwise it's too much shit to verify"). Applies whether the doc is committed, only staged, or kept locally. Applies to docs you author or substantially rewrite, not to docs you only spot-edit. For very short docs (< ~20 lines) a one-line `**TLDR:**` is sufficient. **A more-specific artifact format overrides this length.** Where another rule or workflow doc specifies a fuller header for a particular file type — notably the 2-6 sentence `cc.md` prompt-file TLDR in [`workflows/expts-and-results.md`](../workflows/expts-and-results.md) § Agent Prompt format, which must cover what the agent does, the success criterion, the deliverable, and any load-bearing constraint — that longer spec governs and is not a violation of this rule. The 1-2 sentence form is the default for ordinary docs, not a cap on specialized ones. **Distinct from Hard Rule 4:** Rule 4 is the response-level closing TLDR for chat output; Rule 16 is the file-level Title + TLDR for documents you write to disk. Both apply when you generate a doc inside a response — the chat gets `TLDR-end`; the file gets `# Title` + `**TLDR:**`.
    **Clickable document address (Brando, September 14, 2026; also applies to spot edits).** When creating or editing a repository-hosted Markdown document for the user to read or share, put `**Doc link:** <https://github.com/OWNER/REPO/blob/BRANCH/path/to/file.md>` immediately below its title, separated by blank lines, before its summary. Replace the example with that document's actual full address, derived from the repository remote, intended published branch and file path; encode spaces or other characters as needed. Use Markdown angle-bracket autolink syntax so the full address is visible and clickable, normally blue in the reader's theme. Keep the label exactly **Doc link:**. Do not shorten the visible address to “Doc link” or “Open on GitHub,” or wrap it in inline code or a code block: the user needs both the path hint and a working hyperlink to copy into Google Drive notes. Check the destination and publication state before claiming the link works; if visual verification is unavailable, say so rather than claiming the preview was tested. For an unpublished document, distinguish an intended link from a live one; if no hosting destination is known, omit the link rather than inventing one. This rule does not authorize publishing private material or changing access. Apply on the current edit; do not mass-edit frozen evidence or unrelated documents solely to add links.


    **Google knowledge companion (Brando, 10-16-2026).** Substantial findings, explanations, audits, meeting synthesis and decisions saved as Markdown also belong in the relevant human-readable Google Doc or Slides deck. Brando's standing instruction authorizes that knowledge update without a fresh permission round. Reuse the named or clearly relevant existing destination, preserve its organization and other authors' text, and update the matching section or slides instead of appending duplicates. Put the conclusion and any qualification that changes it in the visible body or slide; keep calculations, methods, uncertainty and provenance in an appendix or speaker notes. Comments may supplement this but are not the only durable home. A link to a local file alone does not make the knowledge available to Google readers.

Prioritize private VeriBench in the Vals deck, followed by VeriBench V1 and Certification Judge; Sanmi’s deck serves the broader research discussion. Preserve the original title and two template slides at the front of each deck, outside the daily research-slide limit; routine consolidation must not replace, retitle or remove them. Preserve useful details in notes/comments or an archive, with material caveats visible. Follow the [daily research slide workflow](../workflows/daily-research-slides.md) for the two exact destinations, evidence checks, consolidation and schedule ownership. ## Trigger Rule 23

23. **CS197 jargon stays out of reader-facing prose.** _Trigger: drafting or revising any reader-facing text in a research paper, blog post, talk abstract, slide deck, or README marketing copy._ Stanford CS197 / Sanmi-lab vocabulary — `bit flip`, `the bit`, `flip the bit`, `vectoring`, `(research) velocity`, `north star`, `killer demo`, etc. — is internal planning shorthand between agents and Brando, NOT writing-style vocabulary. **Allowed:** as a `% LaTeX comment` (e.g., `% bit flip: prior assumes X, we show Y`) to guide structure, or removed entirely. **Not allowed:** in `\section{...}` titles, abstract body, intro prose, figure captions, slides, blog body, README headlines — anything a reviewer or external reader sees. **Why:** ~99% of readers haven't taken CS197 — these terms read as in-group jargon and signal an unpolished paper to top-venue reviewers; Brando has been burned by this before. **How to apply:** when drafting or revising, scan prose for these terms; either delete them, rephrase to plain scientific language ("the assumption we challenge," "our long-term vision," "the headline result"), or wrap as `%` comment. Mirrored briefly in `writing/ml_research/ml_research_writing.md`, `writing/ml_research/write-intro.md`, and `writing/ml_research/write-abstract.md` so each writing skill carries the reminder.

## Trigger Rule 24

24. **Audience-calibrated terminology — translate subfield jargon for the reader.** _Trigger: drafting or revising reader-facing text aimed at an audience outside your subfield (e.g., a formal-methods paper read by ML reviewers, an ML paper read by HCI reviewers, a research blog post read by general technical readers)._ Subfield terms carry different connotations across audiences. Formal-methods *specification* (a logical property to prove) reads to ML reviewers as *prompt spec* or *API spec*; FM *soundness* / *completeness* are alien to most ML readers. **How to apply:** for each technical noun in the abstract / intro, ask "what would the target audience assume this means by default?" — if that's wrong, translate. *specification* → *theorem formulation* / *provable guarantee* / *universal property*; *spec generation* → *extracting a formal property to prove*. Pair with the four related antipatterns in `writing/ml_research/ml_research_writing.md` § Sentence-Level Prose Discipline (#7 audience translation; #8 bridge before escalating; #9 attach critique to fact; #10 name the missing capability, not pejoratives). **Why:** mistranslated jargon makes a reviewer dismiss a paper they didn't understand — the work isn't bad, it's just unreadable to them.

## Trigger Rule 27

27. **Q&A leads with `**A (TLDR):**` direct one-line answer.** _Trigger: answering a substantive question from the user, in chat or in a written explainer doc (`concepts.md`, FAQ, design-decision write-up)._ Format: first content line of the answer is `**A (TLDR):** <one sentence direct answer>`. Then `**Detail.**` (or equivalent) introduces the longer explanation. The TLDR line must (a) actually answer the question, (b) fit on one line, (c) avoid hedging, (d) avoid restating the question. **Why:** Brando reads many auto-generated Q&As per day and cannot scan a wall of text to extract the answer — a missing or weak direct-answer-first makes the explainer unverifiable in practice. **Distinct from Hard Rule 4 (response-level closing TLDR) and Trigger Rule 16 (file-level doc TLDR):** rule 4 is the chat-response TLDR, rule 16 is the file-header TLDR, rule 27 is the per-Q&A direct-answer-first format inside any explainer content. All three can fire at once on a single response that contains a Q&A inside a doc inside a chat reply. Anchored at [`experiments/01_self_hosted_openclaw/concepts.md`](../experiments/01_self_hosted_openclaw/concepts.md) which establishes the format.

## Trigger Rule 41

41. **Score every proposed next task with a predicted priority `x/10`, and list tasks in that order.** _Trigger: you present Brando with one or more tasks, next steps, follow-ups, options, or open items -- a "next steps" list, a project inventory, a dispatch menu, a results hand-back with follow-ups, a quality assurance (QA) finding list you are not fixing yourself. Also the end of a substantive reply, even when the reply itself was not a menu._ Before writing the list, work out in your own reasoning (not in the reply) what each item is worth doing *next* and why: what breaks or slips if it is not done (a deadline, a blocked collaborator, a wrong number in a paper), what it unblocks, how cheap it is relative to that, and how sure you are. Then start every item with one `[p N/10]` tag (`p` means predicted priority; `N` is the score), follow it with a short clause giving the deciding reason, and order the list from highest to lowest score (ties: the cheaper one first). The score predicts how much the item matters next, not its effort or difficulty: **9-10** do it first, a hard deadline or a live wrong result depends on it; **6-8** this week; **3-5** worth doing, nothing depends on it yet; **1-2** close, archive, or drop. The tag and the reason live inside the item's one-sentence budget, not on top of it. If two items cannot be ranked, name the fact that would decide it instead of averaging; if a score hinges on a date or fact you could not verify (an unconfirmed deadline), say so next to the tag. A single follow-up still gets its tag. **Substantive replies end with this list:** three to six items, immediately before the closing TLDR, not after the snapshot. Skip it only for a one-line acknowledgement or when there is genuinely no next action. Do not invent work to fill the list. **A 9 or 10 is an instruction to do it, not a suggestion to wait.** Brando, 10-18-2026: if a next step scores 9 or 10, start it in that same turn without asking, including the top of the list when he says to do the top items. Model spend inside that item is allowed only when the run is already approved, it stays inside the standing pause cap and daily budget, and it does not buy credits, raise a limit, or open a new large unapproved job. If the 9 or 10 would exhaust the remaining budget, overlap another large paid run, or break a hard rule, do the non-spending part and name the limit. A 6–8 waits unless he asks for those items too.
    **Why:** Brando reads these lists between meetings and on a phone. An unordered list of seven "important" strands makes him redo the triage the agent already had the context to do, while an ordered list with a stated reason can be corrected in one line ("no, 74 before 76") instead of re-derived. Stated by Brando 2026-09-08. On 10-18-2026, after two status replies that omitted the list: "I was hoping at the end of each or most responses there is a list on next steps with x/10 ratings on suggestions on what to do."
    **How to apply:** combine with Trigger Rule 36's model + effort recommendation -- the priority tag goes first: `[p 8/10] experiment 76 judge selection, because the paper's headline metric depends on it -- Claude Code Fable 5.1 max`. Keep the scores honest across replies: the same item should not drift from 8 to 4 without a stated reason.

## Trigger Rule 53

53. **Dates humans read are month-day-year (`MM-DD-YYYY`), never year-first.** _Trigger: you choose a name that carries a date (a tmux/byobu session, a file, a directory, a branch) or write a date Brando will read (experiment and task `README.md` files, `results.md` ledgers, `CKPT_<task>.md` checkpoint stamps, results summaries, meeting notes, dispatch manifests)._ Write `MM-DD-YYYY`: `vb-e3-local-publication-09-14-2026` in kebab-case names, `fresh_four_agent_firsttask_09_13_2026.md` in snake_case names, `results_summary_09-14-2026__15-20-00.md`, and `09-14-2026 15:20 PDT` in text and in the Rule 44/45 `Created:` / `Last updated:` stamps (from `date "+%m-%d-%Y %H:%M %Z"`). Prefer no date at all in a name when nothing needs one -- tmux prints creation time, git records commit time, and Rule 44/45 checkpoint filenames stay undated. **Exceptions (machine formats, not human prose):** fields a tool parses keep that tool's format (Jekyll `_posts/YYYY-MM-DD-slug.md` and front-matter `date:`, ISO 8601 inside JSON/CSV/logs, W&B/API timestamps, `~/.codex/sessions/YYYY/MM/DD` paths). **Do not rewrite history:** existing filenames, session names, committed record paths and frozen evidence keep their original spelling; the rule applies to names and text written from now on, and a live record is converted only when it is edited anyway. **Why:** Brando, 09-14-2026, seeing `vb-e2-generation-review-20260913` in `tmux ls` and `fresh_four_agent_firsttask_20260913.md` in `experiments/`: "why is the year at the beginning, it should be at the end. I want month, day, year please" -- and the same for checkpoint file names and experiment README files. No rule had asked for year-first; agents copied the old year-first results-summary and checkpoint-stamp formats, which this rule supersedes.

## Trigger Rule 54

54. **Refer to experiments by their complete folder name, never by a bare number or label.** _Trigger: you mention any experiment, workstream or task in a chat message, TLDR, checkpoint, results ledger, README, status table, commit message or email._ Write the full directory name exactly as it exists on disk -- `experiments/83_E3_vals_direct_api_theorem_coverage/`, `experiments/75_J1_validating_formal_spec_judge_train_val_test/`, `research_archive/experiments/<full name>/` for archived homes -- at least the first time in every section and in every table row, and always in a TLDR. This extends Trigger Rule 39 (a folder name must say what the experiment IS) from how folders are named to how they are cited. **Why:** Brando, 09-15-2026, reading a status report that cited "75", "E3" and "J1": "if you only say like 75 or E3, I'm not gonna know what you're talking about. I prefer if you say the name of the folder, the complete name of the folder for the experiment so that I know what you're talking about. This should be an agents config rule."
