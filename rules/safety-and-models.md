# Safety and models: detailed rules

**Doc link:** <https://github.com/brando90/agents-config/blob/main/rules/safety-and-models.md>

**TLDR:** Read the matching rule sections when routed here by `~/agents-config/INDEX_RULES.md`; this is on-demand policy, not startup reading. Existing rule numbers remain stable.

## Hard Rule 1

1. **Never commit secrets — default is NEVER, even when explicitly asked.** Before any commit (and before any auto-push backstop), scan staged files for: API keys, tokens, passwords, `.env*` (including `.env.local`, `.env.prod`, etc.), `*.pem`, `*.key`, `id_rsa*`, `credentials*`, anything under `~/keys/`, and high-entropy values assigned to names matching `(api[_-]?key|token|password|secret|auth|bearer)\s*[:=]\s*["']?[A-Za-z0-9_\-/+]{16,}`. If anything matches, abort the commit and tell the user exactly which file/line. Once a secret is pushed it must be assumed compromised — git history can't be fully purged (history rewrite + force-push + every existing clone keeps re-leaking), so rotate the credential immediately rather than trying to "scrub" it. **Even an explicit user override ("just commit it") should get pushback first**; the user has stated they don't want to be saying that, so treat such requests as a likely mistake and confirm twice before honoring, then still rotate the credential after. Use env vars or reference `~/keys/` / `~/.ssh/config` instead of inlining secrets.

## Hard Rule 3

3. **QA is explicit opt-in: run it only when Brando asks for it.** QA here means a model-reviewer pass (quality assurance, QA). It runs only when Brando explicitly requests a tier -- "do QA" / "QA it" / "light QA" (one review round), "mega QA" and the other Trigger Rule 10 phrases (the sequential chain) -- or when a runbook or commit tag he set names the tier (for example `[mega-qa]`). No agent starts a reviewer on its own: not for code, shared rules, claims/results, pushes to `main`, end-of-day or "high-stakes" moments, and not because a hook, a project file or an older rule text says QA is "required". **No repo-level hook may force QA on push** (Brando, 2026-09-15: "no repo in my computer should be doing a qa automatically"): a `git push` / `gh pr merge` gate in `.claude/settings.json`, `.claude/hooks/*`, `.git/hooks/*` or CI must stay silent unless a tier was explicitly requested through an opt-in Brando set (env flag such as `<PROJ>_LIGHT_QA=1` / `<PROJ>_MEGA_QA=1`, or a `[qa]` / `[light-qa]` / `[mega-qa]` commit tag); a hook that blocks pushes by default is a bug to fix in that repo, not a rule to obey. **Without a request, still verify the work deterministically** before reporting done -- self-review the diff, `git diff --check`, and the relevant tests / compile / render / targeted grep. **Do not mention QA at all when none was requested** -- no "no QA was run" / "No QA was requested or run" line in replies, checkpoints or commit messages (Brando, 09-16-2026: "The default if qa's aren't the default is to not mention them at all"; the earlier "say in the reply that no QA was run" clause made every reply carry that sentence and was removed). **When QA is requested:** "do QA" or "light QA" = ONE opposite-agent round (Claude Code built -> Codex reviews; Codex built -> Claude Code reviews), the builder applies the findings, verifies them with deterministic checks, done; no automatic re-review. A second round or more only if Brando asks ("otherwise I run out of tokens", 2026-08-20). "mega QA" = Trigger Rule 10. **Separate acceptance requirements are not QA and are unchanged:** benchmark reference (gold) edits still need both model families (Trigger Rule 43), and a scientific model pin or an explicitly required reviewer family stays binding. **Why:** Brando, 09-14-2026: "can we make the qa rule in ac always explicit. I need to say do qa, mega or light for it to be triggered." **CLI-only, no API keys.** Any reviewer dispatch must use locally logged-in approved CLIs (`codex`, `clauded`) with cached subscription/OAuth credentials; never fall back to `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` / `GEMINI_API_KEY`. The deprecated Gemini CLI must not be used. Claude and Codex remain the preferred review families; Brando's September 11 cross-provider recovery authorization also permits other verified subscription clients under Trigger Rule 48 where the canonical review procedure allows them. Explicit required families and benchmark-reference acceptance are unchanged. See [`workflows/qa-correctness.md`](../workflows/qa-correctness.md) for tiers and [`workflows/qa-structural.md`](../workflows/qa-structural.md) for structural checks.

## Hard Rule 8

8. **Strong masters; proportionate execution workers; bounded review and quota recovery.** Keep the strongest configured model for masters and reasoning-critical work. A master explicitly chooses each worker's model and effort for its phase; capable regular workers are the default for well-specified execution. A detailed handoff reduces ambiguity, not the required standard of correctness. Do not lower global defaults to dispatch a worker. Trigger Rule 48 and [`workflows/reliable-agent-dispatch.md`](../workflows/reliable-agent-dispatch.md) define the completion budget, verified handoff and cross-provider recovery contract.
    - **Pinned defaults:** Codex `gpt-6-astra` with `model_reasoning_effort = "ultra"` in `~/.codex/config.toml`; dispatch with `codex exec --dangerously-bypass-approvals-and-sandbox -m gpt-6-astra -c 'model_reasoning_effort="ultra"' "$QA_PROMPT"`. Claude Code `claude-fable-5-1` with `"effortLevel": "max"` in `~/.claude/settings.json` ([template](../claude-code-settings.json)); dispatch with `claude -p --dangerously-skip-permissions --model claude-fable-5-1 --effort max` (`claude-fable-5-1[1m]` for the one-million-token context variant). For a review that must not edit, put that constraint in the review brief while retaining full launch access under Trigger Rule 51; `--full-auto` is removed. Follow Trigger Rule 42 for unattended worker permissions and isolation.
    - **Worker selection:** separate planning, routine execution, the model being measured, and acceptance review. Prefer direct commands for deterministic work; for bounded implementation or research with clear inputs/tests, select a regular reasoning worker and supported effort explicitly. Escalate difficult decisions to the master or a stronger worker based on evidence. Reserve shared subscription allowance for remaining work, reviews and publication; do not send every remote worker at the master's maximum effort. Record exact selected and actual settings, role, rationale and eligible substitutes under Rule 48.
    - **Reviewer selection:** prefer the strongest reviewer from the other company. For ordinary changes, if that model cannot run, try one suitable smaller reasoning model from that company before a fresh strongest-model review from the builder's company. Report the capability reduction and why the candidate meets the task's review needs. A model-specific failure does not prove provider-wide exhaustion. Do not probe smaller models when a provider-wide failure is established. The canonical decision procedure, attempt budget, and reporting fields are in [`workflows/qa-correctness.md` § Review fallback and acceptance](../workflows/qa-correctness.md#review-fallback-and-acceptance); apply it to every review dispatch, including Mega QA.
    - **Acceptance limits:** critical changes retain a strongest-model acceptance review; a smaller critic is advisory only. This includes benchmark reference data, evaluation/scoring integrity, security/authentication, permissions or spending controls, substantive scientific claims/results, uncertain correctness, and shared rules controlling review, permissions, spending, or publication. Each explicitly requested Mega QA acceptance stage also retains the strongest-model requirement. Trigger Rule 43 still requires **both model families at their strongest tier** for every accepted benchmark reference change. A same-company fallback never satisfies a mandatory cross-company check. Keep unresolved requirements pending, even if useful work continues. Model agreement or company diversity is not proof of correctness; reconcile findings against requirements and deterministic checks.
    - **Experiment workloads:** the evaluation backbone, agent under test, evaluation judge, and bulk generation default to regular thinking models such as Claude `claude-sonnet-5` or Codex `gpt-5.6-terra`. Escalate when needed or when Brando explicitly requests a flagship model; record the exact model identifier in results. A benchmark reference edit follows Trigger Rule 43 instead. For executor subscription exhaustion, follow Rule 48: checkpoint, fence the old writer, transfer to an eligible verified subscription client, verify continuation and notify. This never silently changes a pinned model under evaluation, judge, effort, dataset or scoring protocol. If no eligible executor remains, preserve state, notify and arrange a real bounded retry where possible.
    - **Human handoffs:** recommend model and effort proportionately to scope and risk, outside the prompt (Trigger Rule 36). A small mechanical edit may use a regular model; critical review retains the strongest tier. Explicit user model requirements take precedence over fallback; report a blocked required model instead of silently substituting it.
    - **Use authorized balances; never buy an escape hatch:** all model work stays on approved authenticated command-line interfaces (CLIs), per Hard Rule 9. Brando's September 13 instruction permits using his existing Codex and Cursor credits and approved Google/Antigravity plan for authorized work, within the task's recorded budget. Verify the actual account, applicable balance and spending controls, including that already-enabled recharge or postpaid spillover cannot create a new unapproved charge; exhausted included allowance alone does not prove purchased credits are unavailable. Never use provider application programming interface (API) keys, purchase more credits, enable automatic top-ups/uncapped overages, raise an administrator's spending limit, or weaken review requirements to continue. If no eligible reviewer can run within the bounded attempts, report what completed and which acceptance requirement remains unmet.
    - **Keep defaults synchronized:** when the designated strongest models change, update this rule, `~/agents-config/CLAUDE.md`, `~/agents-config/AGENTS.md`, [`workflows/qa-correctness.md`](../workflows/qa-correctness.md), [`machine/macos-ai-apps/ai_agent_automatable_setup_codex_clauded.md`](../machine/macos-ai-apps/ai_agent_automatable_setup_codex_clauded.md), [`claude-code-settings.json`](../claude-code-settings.json), and `~/.codex/config.toml` together. Agent entry points summarize and link here; do not copy the full fallback procedure into each document.

## Hard Rule 9

9. **CLI-only for all LLM work — no agent-authored direct API calls.** Extends the CLI-only mandate from Hard Rule 3 (QA dispatch) to **every** LLM-driven action in every session. **Allowed:** dispatch via the locally-authenticated CLIs `clauded` / `codex exec` / `antigravity`, which use cached subscription / OAuth credentials, are billed against the user's CLI plan with effective per-session ceilings, and leave observable transcripts. The deprecated Gemini CLI is not approved; use a working supported subscription client for Google models. Under Brando's September 11 authorization and Trigger Rule 48, Cursor-hosted models, Grok or other providers may also execute eligible work when their exact client/model, target-host authentication, tools, data access and approved subscription billing or explicitly authorized existing credits are verified under Hard Rule 8's no-new-charge and task-budget requirements. This is not permission to use arbitrary API endpoints, new paid credits or unverified clients. **Forbidden:** authoring or executing any direct LLM-provider API call (`anthropic.messages.create`, `openai.chat.completions.create`, `litellm.completion`, `google.genai.Client(...)`, raw `requests.post` to `api.anthropic.com` / `api.openai.com` / `generativelanguage.googleapis.com`, etc.) unless **Brando wrote the call himself**. An agent must never *author* such code — not in a new script, not in a refactor, not in a one-off notebook cell. Before *executing* any existing script that loads `~/keys/anthropic_*` / `~/keys/openai_*` / `~/keys/gemini_*` / `~/keys/aristotle_*` or sets `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` / `GEMINI_API_KEY`, the agent MUST pause, surface the script path + estimated spend + which experiments will run, and wait for explicit confirmation — silent runs are the failure mode. **Why:** API keys bill per-token with no cap. One agent-driven default (Opus 4.7 in an agent loop, no Batch API discount, ~30 callers all defaulting to the same key) burned **$17,752.98 in 25 days** against `anthropic_bm_key_koyejolab` in May 2026, and the lab confirmed on 2026-05-25 that it cannot absorb that scale of spend. CLI subscriptions self-throttle when a loop misbehaves; raw API self-bills until it drains the account. **How to apply:** (a) if you are about to write `Anthropic(...)` / `OpenAI(...)` / `genai.Client(...)` / `litellm.completion(...)` or paste an `sk-ant-` / `sk-` key into a script, stop and ask Brando whether to use `clauded -p "$PROMPT"` / `codex exec --dangerously-bypass-approvals-and-sandbox -m gpt-6-astra -c 'model_reasoning_effort="ultra"' "$PROMPT"` instead; (b) when reviewing diffs or QA'ing code, flag any agent-authored direct API call as a CRITICAL issue blocking merge; (c) before running any script that reads from `~/keys/*` for an LLM provider, surface path + back-of-envelope cost (`tasks × calls × ~$0.003 Sonnet input / ~$0.015 Opus input` per 1K tokens, multiplied by ~1–10 reps) and wait. **Exception:** Brando-authored API-calling code (commit author = Brando, or explicit "I wrote this, run it now" instruction from Brando in the current prompt) — you may execute it, but still surface estimated spend first. **Counterexample (NOT a direct API call):** invocations of the `clauded` / `codex` / `antigravity` CLIs are exempt, even though they internally reach Anthropic / OpenAI / Google — they are subscription-billed and observable in local transcripts.

## Trigger Rule 10

10. **Mega QA: sequential multi-model review chain.** _Trigger: user **explicitly** says "mega QA", "super QA", "extra careful QA", "deep QA", "final QA", "pre-arXiv QA", "pre-submission QA", or similar. Never auto-triggered — not by `git push`/merge to `main`, not by file-path heuristics, not by a project QA-gate hook. Push-to-`main` gates never start QA on their own (Hard Rule 3: QA is explicit opt-in); only an explicit user request (or a user-set opt-in such as a `[mega-qa]` commit tag) starts it._ Instead of the default single-reviewer QA, run approved reviewer passes **sequentially** — each does full QA (correctness + structural, with authority to fix), then passes the improved code to the next. Default chain (3 stages, preferred Claude/Codex chain; any eligible substitute follows the canonical review procedure and Rule 48): Codex → CC → Codex (if CC built) or CC → Codex → CC (if Codex built) — the builder reviews in the middle (knows intent best); the non-builder CLI takes the first and last (clean-eyes) passes in fresh contexts. If the user asks for more rounds, cycle the chain in fresh contexts. **Per-stage fallback:** apply Hard Rule 8 and the canonical [review fallback procedure](../workflows/qa-correctness.md#review-fallback-and-acceptance). Complete the planned stages using eligible reviewers; an advisory smaller-model pass cannot fill a stage requiring a strongest-model reviewer. Preserve mandatory cross-company checks, including Trigger Rule 43. If no eligible reviewer can run, stop and report the incomplete stage; never claim acceptance from stage count alone or use provider keys. **Manual-only (Brando 2026-08-20):** the mega chain runs only when Brando himself types a trigger; an agent must never choose it on its own — not for end-of-day, pre-merge, pre-sleep, or "high-stakes" moments. An agent never starts any QA tier on its own (Hard Rule 3); a requested light QA is one opposite-agent round. See [`workflows/qa-correctness.md`](../workflows/qa-correctness.md) § Mega QA.

## Trigger Rule 43

43. **Benchmark reference ("gold") data is built, repaired and checked with BOTH model families at their top tier -- never one model alone.** _Trigger: you create, repair, relabel, re-prove, or review the reference side of a benchmark -- gold solutions, ground-truth specifications or theorem statements, gold labels, oracle outputs (expected reference answers), or any dataset that scores are measured against -- for VeriBench or any other benchmark._ Use the smartest current Codex model **and** the smartest current Claude Code model (whichever model identifiers (IDs) Hard Rule 8 names today) on every reference change: no gold edit is accepted on one family's judgment alone -- the other family must have checked it (reviewed the edit, or independently reproduced the result) before it lands. Reference data is the one experiment input exempt from Hard Rule 8's regular "workload" tier: it is correctness-critical, so both models run at the flagship tier (the strongest model tier), while the agent-under-test, the evaluation judge and bulk generation keep following Hard Rule 8 and Guideline 19. Record which model produced and which model checked each landed change (Guideline 19's model-ID requirement, applied per edit). If one family's command-line interface (CLI) is quota-blocked, Hard Rule 8's switch to the other CLI still applies to *continuing the work* (proposing edits, running compiles), but *acceptance* waits until the other family has checked the edit; note the wait in `results.md`.
    **Why:** Brando, 2026-09-08: "for gold ref data we should always be using both codexd and claude (smartest most recent models most capable), because the gold ref data really needs to be correct and unbiased, i.e. not preferred by any model more than another". *Correctness:* the reference is what every score is computed against, so a wrong gold theorem or an incorrect translation between programming languages silently invalidates every downstream number, and a second, independent model catches errors the first is blind to -- the VeriBench gold repair campaign found reference implementations that contradicted their own Python source and theorems that were false as stated (`~/veribench/experiments/75_gold_sorry_closure/results/STATUS.md`, § "Bugs found in the reference set"). *Unbiasedness:* a reference written and checked by a single family risks encoding that family's habits (naming, proof style, what it treats as the "natural" specification), which would tilt the benchmark toward agents from that family; a benchmark measured against a reference one family wrote alone cannot claim to be neutral between families.
    **How to apply:** the recommended shape is the VeriBench phase-2 repair driver `~/veribench/experiments/75_gold_sorry_closure/scripts/repair_gold_reference.sh` (on branch `expt75-repair-driver`, which is where these files live until they land on `main`; check it out in a worktree you own -- `~/veribench-wt-expt75` was the original one and no longer exists): `PROVERS=codex,claude`, the two provers alternate per file behind a mechanical guard, the non-proposing model is the adversarial reviewer (it actively searches for errors in the proposed edit) (`scripts/prompts/repair_prover.md` / `repair_reviewer.md` beside it), and the ledger names both models per edit. Rotating the proposer and logging attribution are the implementation, not extra mandates: any design in which both families at the top tier sign off on every landed reference edit satisfies the rule. Start a new benchmark's reference set from that shape rather than from a one-model pipeline.
