# Workers: detailed rules

**Doc link:** <https://github.com/brando90/agents-config/blob/main/rules/workers.md>

**TLDR:** Read the matching rule sections when routed here by `~/agents-config/INDEX_RULES.md`; this is on-demand policy, not startup reading. Existing rule numbers remain stable.

## Trigger Rule 12

12. **Clean up idle background processes (>24h, confirmed idle).** _Trigger: starting a new session, or starting new monitors/workers._ Before spawning new background processes, scan for existing ones (`ps aux | grep -E "(tail -f|run_worker|until.*sleep.*done)" | grep -v grep`). For each candidate, run a health check before killing — **never kill blindly**: (1) CPU time delta — sample `ps -p $PID -o cputime=` twice 10s apart; if cputime increased, it's actively computing, don't kill (single-sample `%cpu` is unreliable between bursts). (2) Has child processes (`pgrep -P $PID`)? → don't kill. (3) For workers: DB has claimed jobs? → don't kill. (4) For `tail -f`: log file modified in last hour? → don't kill. (5) For `until` loops: wait condition already met? → stuck, safe to kill. **Only kill if ALL checks confirm idle AND running >24h.** Also: name processes descriptively when spawning them so future agents can inspect purpose from `ps aux`. ScheduleWakeup loops must self-terminate when their condition is met.

## Trigger Rule 36

36. **Prompts you hand to another coding agent: recommend model + effort *outside* the prompt, and end the prompt with a TL;DR.** _Trigger: you create or edit a saved scheduled-task prompt, or produce a prompt intended to be run by another coding agent rather than executed by you — a copy-paste block for Claude Code / Codex / Cursor / Antigravity, an experiment runbook (`cc.md`, `agents_v2.md`, `PROMPT_*.md`), a `coding_agent_prompt.md` packet file, or any file whose purpose is "paste this into an agent."_ Two obligations, one trigger:
    - **(a) Recommend a model and effort level, rationale first, in your reply to Brando — never inside the prompt.** Pick **proportionately to the size and risk of the task**, under the proportional-handoff clause of Hard Rule 8: a small mechanical edit does not need the flagship at max effort, and a subtle correctness-critical change must not be run cheaply. Anchor the choice in Hard Rule 8 (currently Codex `gpt-6-astra` + `model_reasoning_effort="ultra"`, Claude Code `claude-fable-5-1` + `"effortLevel": "max"` for reasoning-critical work; the regular thinking tier — `claude-sonnet-5`, a non-Astra Codex tier such as GPT-5.6 Terra — for bulk experiment workloads), and say which side of that split this task falls on. **State the rationale BEFORE the recommendation**, so Brando can disagree with the reasoning and not just the conclusion. **Both the rationale and the recommendation live outside the prompt artifact** — in the chat reply, never in the code block or file that gets pasted. The prompt is what the *other agent* consumes; the model/effort advice is for *Brando*, and burying it inside the handoff both pollutes the prompt and hides the advice where he will not read it.
    - **Remote execution facts are required, not recommendations.** A self-contained runbook or adjacent verified dispatch manifest may and must state the master's selected actual provider/model/effort, exact launch command, eligible fallback order, immutable experiment pins and recovery/notification instructions (Rule 48). The prohibition above concerns hiding human-facing selection advice inside the worker prompt; it does not prohibit these load-bearing execution facts.
    - **(b) End the prompt itself with a TL;DR.** Close the prompt with a 1–2 sentence `TL;DR:` of what it does, which models/tools it runs, and what it produces, so Brando can skim the end of a long prompt and know what he is about to dispatch. This is **additive to Trigger Rule 16**, not a replacement: Rule 16 already puts `# Title` + `**TLDR:**` at the *top* of any generated doc, so a prompt file legitimately carries a TL;DR at *both* ends. Do not "deduplicate" them. **The two ends have different specs and different jobs** — the top TLDR is the fuller one (for `cc.md`-style prompt files, the 2-6 sentence form specified in [`workflows/expts-and-results.md`](../workflows/expts-and-results.md) § Agent Prompt format, covering what the agent does, the success criterion, the deliverable, and any load-bearing constraint; Rule 16 explicitly admits this longer form for prompt files; its 1-2 sentence default governs ordinary docs), while the closing TL;DR is the short 1-2 sentence skim line. Never shorten the top one to match the bottom one.
    **Scope — self-dispatched CLI calls are exempt from (a).** When *you* run the agent yourself (`codex exec …` for a QA stage, `clauded -p …`), just follow the Hard Rule 8 defaults; no recommendation block is needed. But if you deviate from those defaults, state why. Part (b) still applies to any prompt you save to disk for reuse.
    **Scheduled-task prompts must be skimmable.** _Trigger: creating or editing the saved prompt of an automation, scheduled task, or heartbeat (a scheduled follow-up in the same conversation)._ Use a descriptive `# Title` and one closing `**TLDR-end:**` stating the purpose, action, update destination, and existing stopping condition; do not open with `**TLDR-start:**` or `**TLDR:**` (end-only, Brando 09-22-2026, matching Hard Rule 4). If intentionally ongoing, say so; if no stopping condition is specified, say that instead of inventing one. This summary lives inside the saved prompt, not only in the announcing chat; it overrides Rule 16's opening summary and satisfies part (b)'s closing summary, so do not add duplicate blocks. It defaults to 1–2 sentences, but preserve any longer summary required for specialized prompt files. Use Hard Rule 4's project/task tags. Derive the summary from the prompt body without adding instructions; the body governs any conflict. Readability-only edits preserve operational instructions, target, cadence, model, notification settings, and enabled/paused state. This formatting requirement does not invoke part (a)'s human model-recommendation requirement.
    **Why:** Brando dispatches these prompts by hand, often on a phone or between meetings, and the two things he needs to decide fast are *"what do I run this on?"* and *"what does this actually do?"* — neither of which is answerable from a wall of prompt text. Putting the model/effort call inside the prompt is worse than omitting it: the other agent reads instructions meant for the human, and the human never sees the advice. Stated by Brando 2026-09-02.

## Trigger Rule 42

42. **Every dispatched worker runs in its own named byobu/tmux session (a persistent terminal session) -- never headless, never anonymous.** _Trigger: you hand a task to another agent process (Claude Code or Codex, on this machine or on a Stanford Network Analysis Project (SNAP) cluster node) that will run longer than a few minutes, or that Brando might want to look at, attach to, or drive from the phone; in-process subagents (the Agent tool) are for short lookups only._ Before launch, complete Rule 48's explicit model/budget/handoff/recovery plan; launcher defaults are not that plan. SNAP workers run in full-access mode with the Rule 51 pre-approval line in their brief. Start it detached in a session of its own whose name says project and task in kebab case (lowercase words separated by hyphens) (`vb-fix-theorems`, `vb-judge-verdict`, `vb-experiment76-judge-selection`), never a bare number, never a reused name. Locally: `~/agents-config/scripts/deploy_cc.sh --name <name> --cwd <dir> --prompt-file <runbook.md> [--profile cc|ccv|codex] [--model …] [--effort …]` (`cc` selects personal Claude Code, `ccv` its Vals profile, and `codex` Codex; the brief is a runbook file (the worker's written instructions) per Trigger Rule 36; for Claude Code, Remote Control (Claude Code's phone/web access feature) is requested under that name so the session appears on claude.ai/code, and the script exits 0 only once Claude Code's own registry shows a live process in the session; for Codex there is no Remote Control and "started" requires a `codex` process carrying the runbook path and this launch's unique identifier from its opening prompt, running under the pane's shell with the same process identity observed twice, three seconds apart). On SNAP: `scripts/ssh-submit.sh --node <host> --job <file> --tmux-prefix <name> --direct` (Trigger Rule 38 first); its smart-mode agent defaults predate Hard Rule 8 and it has no model-override flag, so put the explicit model and permissions in the job file and use `--direct` until the wrapper is updated, and note that it returns a session named `<prefix>_<job>_<timestamp>` -- report that returned name, not the prefix, in the attach line. One worker per session; concurrent workers get disjoint file ownership and their own git worktree (a separate checkout; the shared checkout has other live sessions in it), a live `results.md` (Trigger Rule 37), and a watch (a periodic status check) that reports when they finish merging their work or their processes stop. Your reply's Snapshot lists the sessions exactly as `tmux ls` prints them (`<name>: 1 windows (created <time>)`) plus the attach line (`byobu attach -t <name>`) and the Remote Control name, so Brando can pick any of them up from anywhere.
    **Why:** a worker in a named session is visible on the agent board under that name, survives the dispatcher's own session ending, can be attached to on the laptop (Claude Code: also driven from the phone), and an interactive Claude Code session can be brought back with the agent board's `--resume-dead` recovery option if the machine restarts (a finished one-shot `claude -p` or a Codex thread cannot); an in-process subagent or a bare `claude -p` in the dispatcher's pane is invisible, dies with its parent, and leaves nothing to attach to. Brando, 2026-09-08, on seeing `vb-fix-thms / vb-judge-verdict / vb-paper-audit` in `tmux ls`: "really helpful... so we always do this type of thing".
    **How to apply:** choose the task name before writing the runbook and use it for the session (locally verbatim; on SNAP as the prefix of the returned name), the git branch and the results ledger section, so the board, `git log`, the ledger and the Rule 44 checkpoint file (`CKPT` means checkpoint; `CKPT_<task>.md`, which `deploy_cc.sh` asks the worker for in its opening prompt) all say the same word; if the same task is re-dispatched, suffix a date or `-v2` rather than killing the old session. Report the model + effort actually typed (Hard Rule 8), and put the `tmux ls` lines in the Snapshot even when only one worker was started. **Two more things Brando asked for on 2026-09-08 ("ideally on a tmux sessions all permission"):** (i) an unattended worker runs with **full permissions** — `codex exec --dangerously-bypass-approvals-and-sandbox` (interactively the `codexd` alias) or `claude --dangerously-skip-permissions` (`clauded`) — because a worker that stops to ask for approval is a dead job; and (ii) anything that may outlive the laptop's attention — a benchmark run, a proof campaign, a multi-hour sweep — is dispatched to a **SNAP node, never hosted on the Mac** (his laptops sleep or shut down mid-run even with keep-awake apps, so the laptop only launches and inspects the remote job). The direct SNAP launcher is `~/agents-config/scripts/snap_dispatch.sh run <name> '<command>'` (detached tmux session named `<name>` on `$SNAP_HOST`, log on node-local `/lfs/<host>/0/brando9/snap_jobs/`, refuses a duplicate name; `tail`/`attach`/`kill` subcommands); `ssh-submit.sh` is the same idea plus the smart-retry agent wrapper. Verify a stop, too: `tmux send-keys C-c` did not stop a mid-attempt driver on 2026-09-08, so after killing a job check `pgrep` for the driver and its children.

## Trigger Rule 44

44. **A long or dispatched run keeps a resumable checkpoint file in the working directory -- so a dead session can retake it.** _Trigger: you start a campaign, sweep, multi-phase experiment, or dispatched worker -- the same class of long or dispatched run Trigger Rule 37 covers. An ordinary multi-step request does not need one._ Write a short plain-text **`CKPT_<task>.md`** (`CKPT` means checkpoint) in the experiment or working directory -- the directory already names the experiment, so the filename names the *task* (e.g. `~/veribench/experiments/75_gold_sorry_closure/CKPT_gold_reference_repair.md`). `CKPT_` is deliberately short so the task still fits in the name, and two concurrent tasks in one dir get two files instead of overwriting each other's state. **Stamp the top with a real clock:** `Created:` and `Last updated:` lines whose value comes from `date "+%m-%d-%Y %H:%M %Z"` (month-day-year, Trigger Rule 53). `Created:` is set once and then left alone; `Last updated:` is re-read from `date` at the moment of every edit -- never a guessed time and never carried over from the previous edit, because a reader who cannot trust the stamp cannot trust the state below it. Refresh it whenever a step lands: what the task is, the step you are on, what has already landed (commits, branches, session names), the exact next command, and any open blocker. Bullets, one screen, no narrative -- it is written for whoever picks the task up, which is usually a fresh instance of you with no memory of the session. It is **not** Trigger Rule 37's `results.md`: that is the *result* record for Brando and carries the numbers and the TL;DR (too long; didn't read) summary, this is the *resume* record for the next agent and carries state and commands. A short run may keep both in one file, but the resume information must exist on disk and not only in a session transcript. For dispatched work, Rule 48 also records input/policy revisions, actual model/effort, attempt identity and budget, quota/error state, ownership transfer and the verified next resume step. Publish meaningful recovery events in the live results record too.
    **Why:** Brando, 2026-09-08, mid-campaign: "Hopefully you put some txt ckpts at 75_ sometimes so you can retake the task in case you die... I wonder if we have a light ac rule for this or something." Same day, on seeing the first one land as a generic `CHECKPOINT.md`: "I think CKPT or ckpt is shorter so the rest of the actual task fits in. Probably dates at the top + time? accurately." A session that dies loses which branch the work sits on, which worker is running under which session name, which review findings were already applied, and which numbers were verified rather than guessed; the next session then either repeats the work or repeats it differently and ships a second set of numbers that disagrees with the first.

## Trigger Rule 45

45. **A master session keeps `CKPT_MASTER_tmux<N>_<agent>_<sid8>.md` at the project's `experiments/` root (`CKPT` means checkpoint; `sid8` is an eight-character session identifier prefix) -- one screen that says how all the strands, workers and pending decisions fit right now.** _Trigger: you have assumed ongoing coordination of other sessions or workers for a project -- you dispatch workers (Rule 42), hold their watches, carry the ranked dispatch list (Rule 41) and the decisions waiting on Brando. Brando calls these "master sessions"; a project may have more than one. An ordinary single-experiment session, a short lookup or review delegation, or a ranked list on its own does NOT qualify._
    - **Name:** `<repo>/experiments/CKPT_MASTER_tmux<N>_<agent>_<sid8>.md` -- the three cells of the agent board row, so file and row name the same thing and two masters never collide. `<N>` is the tmux/byobu persistent terminal session, numeric or named, without window or pane (anything outside letters, digits, `_`, `-` becomes `-`; `none` outside tmux); `<agent>` is `cc` (personal Claude Code) / `ccv` (the Vals Claude Code profile) / `cxd` (Codex); `<sid8>` is the first eight characters of the full Claude conversation identifier (id) or Codex thread id (extend the prefix on a collision). The filename never changes after a move or a resume -- update the header instead. Two processes on one conversation (a session resumed twice) designate one writer. Example: `~/veribench/experiments/CKPT_MASTER_tmux2_cc_857b13e6.md`.
    - **Format:** Rule 44 (plain text, real `Created:` / `Last updated:` stamps from `date`, state + next command), kept to a screen or two that links out to the workers' own `CKPT_<task>.md` files and Rule 37 `results.md` ledgers rather than repeating them.
    - **Sections, in this order:** (1) identity and recovery -- host, absolute current working directory (cwd), full conversation or thread identifier (id), config profile, model + effort, current tmux session/window, and the profile-specific resume command (`clauded --resume <id>` for `cc`, `clauded-vals --resume <id>` for `ccv`, `codex resume <thread-id>` for `cxd`; the board's `--resume-dead` covers Claude Code only); (2) hazards a successor must know first (shared-checkout divergence, memory or quota pressure, idle sessions, hook gotchas); (3) the workers it owns (session name, id, runbook, state, what they landed); (4) its watches -- what each reports, when it ends, whether it survives the session, and the command that starts it again; (5) decisions waiting on Brando with Rule 41 tags; (6) the ranked dispatch list in Rule 41 + 42 form, with any model/effort recommendation outside the linked prompt per Rule 36; (7) what landed (commits, per affected repository); (8) next commands.
    - **Stage by file, never by directory, in a checkout other sessions share.** `git add -A`, `git add .` and `git add <dir>` stage whatever is dirty in that path, including another live session's half-finished work, and the resulting commit then carries changes its message does not describe. Name the files you edited (`git add a.tex b.tex`), or `git diff --stat` the staged set and read it before committing. If it happens anyway: do not rewrite pushed history once anyone has built on it; attach the correction with `git notes add` on the commit, push `refs/notes/commits`, credit the real author of the swept-in hunks, and say so to the session whose work it was. **Why:** Brando, 09-16-2026, had three sessions editing one paper at once; a `git add -A` on the paper dir put a peer's in-progress table restructure inside a commit whose message claimed only two unrelated edits, which makes `git log` lie about who wrote what.
    - **Cadence:** refresh and restamp after every landing, dispatch, decision or hand-back -- not on every message -- and commit and push it like any ledger so it reads from the phone and any machine. Record shared allowance, selected worker roles and the remote recovery owner under Rule 48; a master retiring or sleeping must not leave active jobs with no recovery owner. When the master retires, set `**Status:** RETIRED (successor: <file>)` at the top; never delete, never a generic `CKPT_MASTER.md`. Put the path in your Snapshot whenever you refresh it.
    - **Retired records leave the active list.** Before moving a master checkpoint, verify its explicit retirement and that every owned worker, watcher and pending recovery duty is finished, canceled, or acknowledged by a successor. A stale timestamp or an idle activity badge alone is insufficient. Keep active, blocked or ownership-uncertain coordinators at the experiment root. Move verified retired checkpoints with `git mv` to `experiments/archive/master_checkpoints/` (or an already established master-checkpoint archive), preserving filenames and historical evidence. Maintain an archive index with the old path, new path, retirement reason and successor; update live links and relative links inside moved files, while frozen evidence retains its historical identity. Do not create a root-level placeholder that recreates the clutter.
    - **Readable dates, stable identities.** Keep `Created:` fixed and refresh `Last updated:` from the real clock using `MM-DD-YYYY HH:MM TZ` (for example, `09-13-2026 19:16 PDT`; Trigger Rule 53); stamps written earlier in `YYYY-MM-DD` stay valid. Add `Retired:` or `Archived:` when those events are verified, without inventing an earlier retirement date. Record the latest recovery state at the top and mark old chronology as historical. Do not rename a live checkpoint on each update or create dated duplicates for the same conversation; stable filenames and the in-file timestamps serve different purposes.
    **Why:** Brando, 2026-09-08: "You are a master session ... one of my main sessions that deals with my entire project and lots of other sessions we are managing. So I think you should have a CKPT_MASTER_tmux_NUM_CC_sessionID.md file at experiments." A master's transcript is the largest in the project and the slowest to re-read; when it dies, resuming brings the conversation back but not a two-minute answer to "what was running, what landed, what does Brando still owe a decision on" -- that answer is this file, and it doubles as the project's live status page.

## Trigger Rule 48

48. **Plan for completion before dispatch; recover access and eligible providers without losing work.** _Trigger: dispatching or supervising a long/unattended worker, inheriting a master role, or anticipating/hitting an authentication, allowance or credit failure._ Brando's September 11 and 13 instructions apply across providers, on both Macs and SNAP. `master agent:` explicitly designates the coordinator; infer that role when already coordinating under Rule 45, without asking for a label. Read [`workflows/reliable-agent-dispatch.md`](../workflows/reliable-agent-dispatch.md), the canonical procedure.
    - **Select by phase and budget.** Keep the master capable (normally strongest/maximum effort), use direct commands or regular workers for well-specified execution, and choose model and effort explicitly. Record current shared-account usage/reset evidence or unknown, a conservative next-phase estimate, finishing/review reserve, concurrency and a short verified fallback order. Default reconsideration triggers are 25% remaining and no new expensive batch at 10%; these are planning heuristics, not provider guarantees. Unknown usage does not authorize an unmeasured fan-out.
    - **Deliver a resumable contract.** Save the detailed runbook, dated `CKPT_<task>.md`, live `results.md` and dispatch manifest in the experiment/owned working directory. Push scanned task-owned material, fetch its exact revision on the target, verify file hashes (or a durable artifact transfer), and obtain the worker's input/model/process acknowledgement plus a real first action. A local file, queued prompt or terminal alone is not a handoff. Preserve private runtime paths and immutable scientific inputs.
    - **Make recovery survive the master and primary model.** One named remote recovery owner and a non-model watchdog must observe actual processes, child jobs, errors and completion evidence. Record and verify its executable, state, cadence, notification path, stop/retry condition and reboot behavior; simulate a harmless failure before calling the job unattended-ready. Existing launchers or observation-only monitors do not gain automatic failover from this rule. A laptop-only watch is insufficient.
    - **Recover routine sign-in autonomously.** Classify transport, authentication, model entitlement, included allowance, prepaid balance and administrator limits separately. For an already-authorized account/client, the recovery owner completes the vendor-supported sign-in or refresh, including driving the signed-in Mac browser for a remote worker, without a preliminary permission question. Serialize login per credential profile, preserve healthy child jobs, never clone an active refresh credential across machines, and verify target login plus the next useful bounded action. Ask only for an actual required human step or materially new access; no password/verification bypass. A sleeping Mac or inaccessible browser is a real recovery dependency, not a reason to claim automatic renewal works. Follow [authentication recovery](../workflows/reliable-agent-dispatch.md#authentication-recovery) for bounded attempts, secret handling and continuation.
    - **One policy, verified clients per machine.** Keep the shared policy in agents-config and record each reachable host's actual client/version, account profile, supported models/efforts, authenticated billing route, budget, permissions, callback and last useful verification. Codex, Claude Code, Cursor Agent and Antigravity are candidates, not interchangeable accounts or proven installations. Use deterministic commands first and capable regular workers for clear execution; preserve strong masters, scientific pins and required acceptance. Pull and verify the policy revision on each target; an offline Mac remains explicitly unsynchronized until reachable.
    - **Continue safely and report.** Before exhaustion, checkpoint and reduce needless context/concurrency or select a suitable alternative. On failure, preserve partial work, lock recovery, confirm the old writer stopped or adopt its healthy child job, then resume the smallest missing unit on the next verified subscription client. Codex, Claude, supported Google-model clients, Cursor-hosted models, Grok and other providers are eligible only when the role, target client, actual model/effort, tools and billing are verified. Keep one writer, bounded attempts, original findings and scientific pins; never use provider keys, purchase credits, invent access or repeat completed work. Reviewer eligibility/attempts remain governed by Hard Rule 8; benchmark-reference acceptance still requires both strongest Claude and Codex. If no eligible route remains, preserve an explicit blocker and actual bounded wake-up when possible; never claim finished.
    - **Notify and finish.** Record each meaningful quota-risk/failover event durably and notify the master plus `brando.science@gmail.com` without carbon copies; deduplicate by job/incident/state, and report delivery failures. Completion means verified requested outputs, checks, required review and main publication with its completion record; it does not mean a successful launch, reset, model response or provider switch. Rule 46 still owns the final landing receipt.

## Trigger Rule 52

52. **Agent-board freshness is part of running a job.** _Trigger: any agent starts, resumes, supervises or reports a task shown on the agent board._ Applies to Claude Code, Codex and other agents. The execution owner provides small, atomically written status receipts after meaningful changes and a non-model liveness update about every 120 seconds. Include a stable experiment run identifier shared by acknowledgement/progress/driver/watchdog receipts, the canonical experiment path, observation time, current coordinator and driver identities (process identifier, start time and boot identity), phase, completed/missing counts and explicit blockers. Preserve the run identifier across coordinator restarts; create a new one for a distinct experiment run. Never include credentials or full prompts.
    - The board uses deterministic polling, normally every 120 seconds while the host/app is available; local display rendering can remain every 20 seconds. No model call is required for each poll. Use a bounded reasoning check only for an ambiguous state, failure, recovery or meaningful milestone; respect the user's current model/effort and budget instructions.
    - Verify that the actual board row names the canonical experiment and reflects a real receipt/process after launch or a status change. A green coordinator is not proof of generation, scoring or completion. Show coordinator activity, worker/driver activity and result progress separately; never label a workstream such as E4 as experiment 4 by extracting its digits.
    - Surface failed polls, missing identities, old receipts and disconnected hosts as stale or unverified, with timestamps. Cached evidence never proves current activity. Keep last known counts visible but clearly qualified; do not fabricate zeros, freshness or completion. A sleeping Mac cannot promise continuous local updates.
    - Use the shared board collector, not a second competing renderer or one language-model call per update. Existing workers without compatible receipts remain explicitly unverified until their execution owner adds them. Share the rule through the Claude/Codex entry points and the dispatch instructions; record which live agents/hosts acknowledged it instead of claiming every running context automatically reread the file. See [the board implementation contract](../machine/mac.md#agent-board-which-agent-is-in-which-tmux-window).

## Trigger Rule 57

57. **Decide it yourself and proceed -- do not stop to ask Brando.** _Trigger: you are about to ask the user a question that gates the work: a clarifying question, an approval request, an `AskUserQuestion` menu, a "should I do A or B?", or a dispatched worker escalating a routing, configuration or scope choice back to you._ Make the call. Pick the option you would have labelled **(Recommended)**, say in one or two lines what you chose and why, keep going, and write the decision where the work lives (the experiment ledger, `CKPT_<task>.md`, the commit message, the worker's shared state) so it is visible and reversible. When the choice genuinely needs judgement you do not have, spin a subagent to make it -- hand it the options, the evidence and the constraints, ask for a pick plus a one-paragraph rationale, and then act on that pick. Route the question to another agent, never to Brando. **The only things still worth stopping for:** a destructive or irreversible action on shared systems (deleting data or experiment evidence, force-pushing, rotating a credential, killing another owner's live run), new spend past an approved cap or any new purchase, something published outward in his name (an email, a Slack message to collaborators, a public repo, arXiv, a tweet), or an action that would break a Hard Rule. Even then, do every part of the task that does not depend on the answer first, and put the specific proposed action in front of him rather than an open question. A decision made and stated is cheap to correct; a stalled task is not. **Why:** Brando, 09-16-2026, after an orchestrator paused the E2 finish to ask him which route to authorise: "do whatever you think is best, if you need another agent to make decisions like the above questions feel fre to spin it and use it to choose the best prefered answer, likely let's put it yes as an ac rule, it's really annoying how claude ask me for shit, just finish it and decide something smartlly, just do the recommended ones please". This is the general form of Rule 51 (SNAP work is pre-approved) and Rule 8 (commit and push once verification passes, without asking).

## Trigger Rule 58

58. **Finish the task with whatever agent is available -- never stall on your own limits or tool gaps.** _Trigger: the work is blocked by your own capacity rather than by the task itself: a quota or usage limit, a rate limit, a model that will not do it, a skill gap, missing permissions, **a lack of built-in tools (e.g., missing browser, computer-use, or email connector)**, or a job long enough that doing it serially would miss the moment._ **Never bounce a task back to the user suggesting they do it manually or via a slash command.** Delegate and parallelise across every agent Brando has installed instead of reporting back empty: your own subagents, `codex exec` / `codexd` (GPT-6 Astra), `clauded` and `clauded-vals` (Claude on the personal and Vals profiles), `antigravity` (Google -- it replaces the deprecated Gemini CLI, which stays uninstalled), Cursor, Mistral, Grok, Harmonic/Axiom, and whatever else `~/agents-config/scripts/auto-update-tools.sh` keeps fresh. Mixing vendors inside one task is expected, not a last resort, and a SNAP worker can hold a second CLI open beside it. **What does not bend:** Hard Rule 9 -- every model call goes through an approved CLI, never a direct provider API key and never hand-written `anthropic` / `openai` / `google.genai` client code; a project's funding rule still binds its *measured* calls (VeriBench generation and judging stay on the Vals-funded route no matter who coordinates); Hard Rule 8's smartest-tier default for reviews; and no secret ever enters a prompt. Record which agent and model did which piece, in the results ledger, the checkpoint or the commit message, so every artifact is traceable to its author. When one CLI is quota-blocked, switch to another and say so in the report -- "I ran out of quota" is a routing problem, not a finished task. **Why:** Brando, 09-30-2026: "I did try to install all connectors and all permissions... things shouldn't be failing unless it's a genuinely difficult task." Pairs with Rule 57 (decide, do not ask) and Rule 51 (SNAP work is pre-approved).
